      ```markdown
      # Helm Chart Hardening — Reference App

      ## System State
      - Existing chart: reference-app/helm/reference-app/
      - Chart version: 1.0.0 (apiVersion: v2)
      - Services: api-gateway (8080), catalog (8081), worker (8082), dashboard (3000, NodePort 30080)

      - No HorizontalPodAutoscaler — no autoscaling under load

      - No ServiceMonitor — Prometheus cannot discover service metrics
      - No NOTES.txt — helm install shows no usage instructions

      - Must pass helm lint with zero errors and zero warnings
      - Must pass kubectl apply --dry-run=client on rendered output
      - All new resources must be toggleable via values.yaml (enabled: true/false pattern)
      ```

    **Phase 1: Brainstorm (15 min) — "What needs to change?"**

    **Phase 2: TDD — RED (20 min) — "Define what success looks like before writing code"**

    The TDD "test" for Helm charts uses `helm lint` and `helm template | kubectl apply --dry-run=client` as the verification toolchain (no extra installs required per research findings).

    Step 1: Establish baseline — run `helm lint reference-app/helm/reference-app/` to confirm current chart is valid
    Step 2: Define what the enhanced chart MUST produce — write a checklist:
      - `helm template` output MUST contain a HorizontalPodAutoscaler resource
      - `helm template` output MUST contain a PodDisruptionBudget resource
      - `helm template` output MUST contain a ServiceMonitor resource
      - `helm install --dry-run` output MUST show NOTES.txt content
      - All deployments MUST have resource limits set

    Step 3: Create a verification script `verify-chart.sh`:
    ```bash
    #!/bin/bash
    CHART_DIR="reference-app/helm/reference-app"
    ERRORS=0

    # Lint
    helm lint "$CHART_DIR" || { echo "FAIL: helm lint"; ERRORS=$((ERRORS+1)); }

    # Render and check for required resources
    RENDERED=$(helm template test-release "$CHART_DIR" -f "$CHART_DIR/values.yaml")

    echo "$RENDERED" | grep -q "kind: HorizontalPodAutoscaler" || { echo "FAIL: no HPA found"; ERRORS=$((ERRORS+1)); }
    echo "$RENDERED" | grep -q "kind: PodDisruptionBudget" || { echo "FAIL: no PDB found"; ERRORS=$((ERRORS+1)); }
    echo "$RENDERED" | grep -q "kind: ServiceMonitor" || { echo "FAIL: no ServiceMonitor found"; ERRORS=$((ERRORS+1)); }

    # Dry-run
    echo "$RENDERED" | kubectl apply --dry-run=client -f - || { echo "FAIL: dry-run failed"; ERRORS=$((ERRORS+1)); }

    # NOTES.txt
    helm install test-release "$CHART_DIR" --dry-run 2>/dev/null | grep -q "NOTES:" || { echo "FAIL: no NOTES.txt"; ERRORS=$((ERRORS+1)); }

    if [ $ERRORS -eq 0 ]; then echo "ALL CHECKS PASS"; else echo "$ERRORS checks failed"; fi
    ```

    Step 4: Run the verification script — it MUST FAIL (RED). The current chart has none of these resources. This is the TDD "red" state.
    - Expected result: Multiple "FAIL" lines showing missing HPA, PDB, ServiceMonitor, NOTES.txt

    **Phase 3: Implement — GREEN (20 min) — "Generate the minimum code to pass"**
    - Prompt AI: "Using the CLAUDE.md context and the verification checklist, generate Helm templates for: hpa.yaml, pdb.yaml, servicemonitor.yaml, NOTES.txt. Also add resource limits to all existing deployment templates. Each resource must be toggleable via values.yaml."

    - Run verification script again — it MUST PASS (GREEN)
    - Expected result: "ALL CHECKS PASS"
    - If any check still fails, this feeds into the Debug phase — do NOT manually fix yet

    **Phase 4: Debug (10 min) — "Fix what the AI got wrong"**
    - This phase uses REAL errors from AI generation (per D-06 — no planted bugs)
    - Common AI generation errors for Helm charts:
      - Wrong `apiVersion` for HPA (should be `autoscaling/v2`, AI may generate `autoscaling/v2beta2` which is removed in K8s 1.26+)
      - Wrong `matchLabels` selector (must match the deployment's selector, not the chart name)
      - ServiceMonitor using wrong port name (must match the port name in the Service resource)
      - NOTES.txt missing template functions (should use `{{ .Release.Name }}`)
    - Apply the Systematic Debugging workflow:
      1. Read the error output from helm lint or kubectl dry-run
      2. Trace backward: which generated file causes the error?
      3. Form hypothesis: what specific value is wrong?
      4. Apply smallest fix, re-run verification
    - Key teaching point: AI-generated IaC errors are predictable categories. After seeing a few, you develop pattern recognition for what to check.

    **Phase 5: Verify + Code Review (15 min) — "Prove it works, then improve it"**

      ```bash
      helm lint reference-app/helm/reference-app/
      helm template course-app reference-app/helm/reference-app/ -f reference-app/helm/reference-app/values.yaml | kubectl apply --dry-run=client -f -
      helm install course-app reference-app/helm/reference-app/ --dry-run
      ```
    - All three must succeed with zero errors

    - Final verification run after review changes
    - Compare output against the reference chart — `diff` the enhanced templates against the baseline to see exactly what was added
