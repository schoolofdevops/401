    - `# Superpowers for Infrastructure as Code` — intro: The Superpowers are not generic coding practices. They are specific workflows that become dramatically more powerful when combined with AI coding agents applied to infrastructure code.

    - `## Why IaC Needs Superpowers` — IaC is uniquely suited for AI-assisted workflows: declarative (testable without running), domain-specific (provider schemas constrain output), and high-consequence (wrong config = outage). The Superpowers add discipline that prevents the "generate and pray" anti-pattern.

    - `## The Superpowers Cycle` — overview diagram (text-based):
      ```
      Context (CLAUDE.md) → Brainstorm → TDD (RED) → Implement (GREEN) → Debug → Verify + Review
      ```
      Each step explained in 2-3 paragraphs, using concrete IaC examples from the lab:

    - `## Superpower 1: TDD for Infrastructure` — explain the Iron Law applied to IaC. How `helm lint` failures are the "red" test for Helm. How `terraform test` with `mock_provider` is the "red" test for Terraform. Key insight: writing the test first CONSTRAINS what the AI generates. Instead of "write me a Terraform module" (unbounded), you say "write code that passes THESE tests" (bounded).

    - `## Superpower 2: Systematic Debugging of AI-Generated IaC` — explain the 4-phase approach applied to AI generation errors. Common error categories: wrong API versions, wrong attribute names, missing required fields, wrong resource relationships. The 3-Fix Rule: if you have tried 3 manual fixes and the AI keeps generating the same error pattern, question the CLAUDE.md context — the problem is likely in what the AI is seeing, not in the AI itself.

    - `## Superpower 3: Verification Before Completion` — explain the Gate Function for IaC. "It works on my machine" is not verification. Running `helm lint`, `helm template | kubectl apply --dry-run`, `terraform validate`, `terraform test` IS verification. The difference between "I think the chart is correct" and "helm lint exits 0 and dry-run shows 5 resources created."

    - `## Superpower 4: Code Review for Generated Code` — explain the 5 dimensions applied to IaC. Why generated code needs MORE review, not less: AI may produce syntactically valid but semantically wrong infrastructure (e.g., HPA with minReplicas > maxReplicas, CloudWatch alarm with evaluation_periods = 1 causing false positives). The review catches intent mismatches that tests cannot.

    - `## Context Engineering: The Starter That Replaces Starter Code` — explain D-10 philosophy. Traditional approach: scaffold with TODOs. Superpowers approach: CLAUDE.md with system state + constraints + goals. Why this produces better output: the AI gets operational context (what exists, what is missing, why it matters) rather than syntactic hints (fill in this blank).

    - `## When to Apply Superpowers to IaC` — decision framework:
      - Greenfield module (new Terraform module, new Helm chart): full cycle — brainstorm through review
      - Existing module enhancement (add resources to existing chart): skip brainstorm, start at TDD
      - Bug fix in existing IaC: start at Debug phase, add regression test
      - Quick one-off change: Superpowers may be overkill — use judgment (link to Module 6 plan modes)

    - `## Key Takeaways` — 5 bullet points summarizing

      **Helm Errors:**
      | Error | AI Mistake | Fix |
      |-------|-----------|-----|
      | Wrong apiVersion for HPA | `autoscaling/v2beta2` | Use `autoscaling/v2` (v2beta2 removed in K8s 1.26+) |
      | matchLabels mismatch | Chart name instead of deployment selector | Must match deployment `.spec.selector.matchLabels` |
      | ServiceMonitor wrong port | Port number instead of port name | Use the `name` field from the Service spec |
      | NOTES.txt no templating | Hardcoded release name | Use `{{ .Release.Name }}`, `{{ .Release.Namespace }}` |

      **Terraform Errors:**
      | Error | AI Mistake | Fix |
      |-------|-----------|-----|
      | Wrong AMI filter | `name = "amzn2-*"` without owner | Add `owners = ["amazon"]` to data source |
      | Wrong metric name | `cpu_utilization` | Use `CPUUtilization` (exact AWS name) |
      | Wrong comparison operator | `GreaterThanOrEqualToThreshold` | Use `GreaterThanThreshold` for standard alarm |
      | Missing SNS protocol | Defaults to wrong protocol | Explicitly set `protocol = "email"` |

    - `## Systematic Debugging Phases` — compact 4-phase reference:
      1. Investigate: Read error, reproduce, check recent AI output
      2. Pattern: Find working example, compare what is different
      3. Hypothesize: One variable, smallest change
      4. Fix: Failing test first, single fix, verify

    - `## Code Review Dimensions for IaC` — compact 5-dimension checklist:
      1. Code Quality: naming, DRY, no hardcoded values
      2. Architecture: resource relationships, data flow, dependency ordering
      3. Testing: assertions cover all resources, edge cases (empty values, zero replicas)
      4. Requirements: all CLAUDE.md items present, constraints met
      5. Production Readiness: free tier compliance, variable defaults, documentation

    **Questions to author:**

    **Q1: TDD for IaC** — "When applying TDD to Helm chart development, what serves as the 'failing test' (RED phase)?"
    Correct: `helm lint` showing the chart is valid but missing required production resources (HPA, PDB). Wrong answers: `helm install` failing on the cluster, manually reviewing YAML for missing fields, `kubectl describe` showing missing pods.
    Explanation: TDD for Helm uses `helm lint` and template rendering as the test harness. The RED state is when lint passes (chart is syntactically valid) but rendered output is missing the resources you defined as requirements in your verification script.

    **Q2: mock_provider purpose** — "What is the primary benefit of using `mock_provider` in Terraform tests?"
    Correct: Tests run without AWS credentials or real API calls — fully offline TDD. Wrong: Faster test execution, better error messages, automatic resource cleanup.
    Explanation: mock_provider intercepts all provider API calls, returning synthetic responses. This enables the TDD cycle to run entirely offline — you write tests first, generate code, and verify without needing AWS access or incurring costs.

    **Q3: Context-first approach** — "In the Superpowers workflow, why does the lab use a CLAUDE.md file instead of starter code with TODO comments?"
    Correct: CLAUDE.md provides operational context (system state, constraints, goals) that produces better AI generation than syntactic hints. Wrong: CLAUDE.md is required by the tool, TODO comments confuse AI, starter code is harder to maintain.
    Explanation: The Superpowers approach treats context as the input, not code skeletons. A CLAUDE.md describing "what exists, what is missing, and why it matters" gives the AI a rich operational frame that produces more complete and contextually appropriate output than "fill in this function body."

    **Q4: Debugging AI-generated IaC** — "After AI generates a Terraform module, `terraform test` fails with 'CPUUtilization' not matching. Which debugging phase applies first?"
    Correct: Phase 1 (Investigation) — read the error output and trace it to the specific resource attribute. Wrong: Phase 3 (Hypothesis — guess the fix), Phase 4 (immediately write a fix), restart the generation.
    Explanation: Systematic debugging always starts with investigation. Reading the exact error and tracing it to the resource attribute (metric_name in aws_cloudwatch_metric_alarm) is faster than guessing. The error message tells you exactly which assertion failed and why.

    **Q5: Verification vs assumption** — "Which statement represents proper verification of a Helm chart, not just an assumption?"
    Correct: "`helm template | kubectl apply --dry-run=client` exits 0 and shows 5 resources created". Wrong: "I reviewed the YAML and it looks correct", "helm lint passed so the chart is production-ready", "The AI said the chart is complete".
    Explanation: Verification requires running a command and reading its output — the Gate Function (Identify, Run, Read, Verify, Claim). "Looks correct" is an assumption. `helm lint` passing only validates syntax, not completeness. AI assertions are not evidence.

    **Q6: Code review for generated code** — "Why does AI-generated IaC need MORE code review than human-written IaC, not less?"
    Correct: AI can produce syntactically valid but semantically wrong infrastructure (e.g., HPA with minReplicas > maxReplicas). Wrong: AI code has more bugs, AI does not understand Terraform, generated code is always lower quality.
    Explanation: AI generation excels at syntax — the code will parse, validate, and often pass basic tests. But semantic correctness (does the config DO what you intended?) requires human review. An HPA with minReplicas: 5 and maxReplicas: 3 will pass `helm lint` but break at deploy time.

    **Q7: When to skip Superpowers** — "For which task would applying the full Superpowers cycle be LEAST appropriate?"
    Correct: Changing a single variable default in an existing, tested Terraform module. Wrong: Building a new Helm chart from scratch, adding monitoring to an existing module, debugging a failing deployment pipeline.
    Explanation: The Superpowers cycle is designed for substantive IaC work — new modules, new resources, complex changes. For a one-line variable default change in an already-tested module, the overhead of brainstorm/TDD/review exceeds the risk. Use judgment — link to Module 6 plan mode selection.
