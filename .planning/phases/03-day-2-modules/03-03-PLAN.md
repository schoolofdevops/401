    - id: module-05a-concepts

    - sidebar_label: "Concepts"

    Content sections:

    1. **Why "Just Ask the AI" Fails for Infrastructure**
       - The infrastructure specificity problem: generic AI output is dangerous for IaC (wrong API versions, missing security constraints, hallucinated attributes)
       - DevOps analogy: It is like asking a new hire to "just deploy this" without giving them access to the architecture diagram, runbooks, or constraints doc
       - Real example: Show a bare request ("Write a Helm chart for my app") vs the same request with structured context (4 layers) — contrast the output quality
       - The cost of wrong infrastructure: A bad prompt wastes tokens; bad IaC wastes hours in debugging or causes production incidents

    2. **The 5-Phase Structured Workflow**
       - Brainstorm → Design → Blueprint → Implement → Validate
       - DevOps analogy: Like a change management process — RFC → design review → staging → production → monitoring
       - Why each phase matters: Brainstorm catches missing requirements, Design locks architecture, Blueprint creates scaffolds, Implement fills details, Validate proves correctness
       - Anti-pattern: Skipping straight to Implement (like deploying without a design review)

    3. **Gap Analysis as Context Engineering**
       - The baseline → production gap is a context engineering exercise
       - What the AI needs to know: what exists (baseline), what's missing (gap), what constraints apply (environment)
       - DevOps analogy: Like a security audit — you can not fix what you have not inventoried

    4. **Validation: The Humans Still Matter**
       - AI-generated IaC must be validated with the same rigor as human-written IaC
       - `helm lint`, `terraform validate`, `kubectl apply --dry-run`, `actionlint`
       - DevOps analogy: Like code review — the AI is a junior engineer who writes fast but needs senior review

    Content sections:

    1. **Context Engineering: The Core Skill**
       - Recap from Module 1: context engineering is about what the AI sees, not how you ask
       - CLAUDE.md as system context — the most teachable artifact
       - The 4-layer context model applied to infrastructure: Task (output), Role (actor), System (environment), Procedure (constraints)
       - DevOps analogy: CLAUDE.md is like a Kubernetes ConfigMap — it defines the environment the workload runs in
       - Why it matters: Without system context, AI produces generic, dangerous infrastructure code

    2. **Structured Workflows: From Ad-hoc to Repeatable**
       - The GSD pattern: discuss → plan → execute → verify
       - DevOps analogy: Like CI/CD for AI work — instead of ad-hoc deployments, you have a pipeline
       - Why structure matters: Multi-file infrastructure changes require coordination, not just generation
       - The traceability benefit: Every decision in GSD is logged in STATE.md — audit trail for IaC decisions

    3. **Memory: Cross-Session Persistence**
       - The problem: AI tools forget everything between sessions
       - DevOps analogy: Like stateless containers — each session starts fresh unless you mount persistent storage
       - Two approaches: claude-mem (automatic capture, semantic search) vs MCP memory (explicit, protocol-based)
       - When to use memory vs context vs plans: Memory for decisions/patterns that recur; context for current session facts; plans for structured multi-step work

    4. **Plan Modes: Think Before You Execute**
       - Quick plans (/plan) vs production plans (GSD plan-phase)
       - DevOps analogy: Like the difference between running `kubectl apply` directly vs going through a change management process
       - When to plan: Multi-file changes, unfamiliar territory, production impact
       - When to just execute: Single-file edits, well-understood patterns, low-risk changes

    5. **Extending AI with Disciplined Workflows**
       - TDD, debugging, code review as "superpowers" — structured approaches that make AI more reliable
       - DevOps analogy: Like adding linting and testing to a CI pipeline — the AI is the developer, the workflows are the guardrails
       - Key insight: AI produces better output when given a structured process, not just a blank canvas
