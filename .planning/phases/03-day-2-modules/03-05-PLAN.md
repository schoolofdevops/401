    **concepts.mdx** (per MOD6-05 — AI failure modes in infrastructure generation):
    - id: module-06-concepts
    - title: "Concepts: AI-Assisted Infrastructure as Code"
    - sidebar_label: "Concepts"
    - sidebar_position: 1

    Content sections:

    1. **AI Failure Modes in IaC Generation**
       - Schema drift: AI generates attributes from an older provider version (e.g., deprecated `security_groups` instead of `vpc_security_group_ids` in aws_instance)
       - Hallucinated attributes: AI invents resource attributes that do not exist in the provider schema
       - Version mismatch: AI uses Terraform syntax from a different version (e.g., `count` vs `for_each` inconsistencies)
       - Missing dependencies: AI forgets implicit dependencies (e.g., SNS subscription before topic)
       - DevOps analogy: Like a junior admin who memorized docs from 2 years ago — their knowledge is real but outdated and sometimes wrong

    2. **Why AI Errors in IaC Are Especially Dangerous**
       - Infrastructure errors have blast radius: a bad Terraform apply can destroy resources
       - `terraform plan` is your safety net — always review before apply
       - GitOps amplifies errors: ArgoCD auto-syncs, so bad YAML deploys automatically
       - DevOps analogy: Like auto-scaling on a misconfigured health check — the system faithfully does the wrong thing, at scale

    3. **Context Engineering for IaC Quality**
       - CLAUDE.md as the IaC-specific context file: versions, constraints, resource types
       - The guided generation pattern: provide schema + constraints + examples, not just intent
       - Why generic requests produce dangerous output: "Write a Terraform module" vs "Write a Terraform module for AWS provider 5.x using t2.micro free tier with CloudWatch basic monitoring"
       - DevOps analogy: Like writing a Dockerfile without specifying the base image version — you get whatever the AI thinks is current

    4. **Validation as a Non-Negotiable Step**
       - `terraform validate` catches syntax errors, `terraform plan` catches logic errors, `terraform test` catches behavioral errors
       - `kubectl apply --dry-run=client` catches K8s schema errors
       - `helm lint` + `helm template` catch Helm template errors
       - ArgoCD sync status catches GitOps drift
       - The validation hierarchy: syntax -> schema -> behavior -> integration
       - DevOps analogy: Like a CI pipeline — each stage catches different classes of errors

    5. **Real vs Mock: When Each Path Is Appropriate**
       - Real AWS: best for learning, most realistic, requires credentials
       - mock_provider: validates logic without cloud access, catches threshold/config errors
       - Dry-run: validates syntax and schema without side effects
       - DevOps analogy: Like testing stages — unit (mock) -> integration (dry-run) -> production (real apply)

    7. What is the difference between `terraform test` with mock_provider and `terraform plan` against real AWS? (mock_provider validates logic without credentials/cost; plan against real AWS validates against actual API schemas and state)
