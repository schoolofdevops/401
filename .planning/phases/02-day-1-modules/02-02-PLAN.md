Cover these concepts (per MOD1-04), each with a clear explanation and a DevOps analogy where it fits naturally:

**1. Tokenization** (~20 lines)
- What: Text broken into subword units (not words, not characters). "Kubernetes" might be 2-3 tokens. JSON is token-expensive.
- DevOps analogy: "Like log parsing — raw text gets broken into structured units before processing. Just as a log parser splits on delimiters, a tokenizer splits on learned patterns."
- Practical: Show a token count example. "This CloudWatch alarm JSON is ~150 tokens. Your runbook context adds ~400 tokens. You're paying per token."
- Reference: Link to OpenAI tokenizer or Anthropic's documentation for hands-on exploration.

**2. Context Window** (~20 lines)
- What: The fixed amount of text (tokens) the model can see at once. Claude: 200K tokens. Gemini 2.5 Flash: 1M tokens. This is THE constraint.
- DevOps analogy: "Like container memory limits. Exceed it and the process gets OOM-killed. Unlike containers, you can't just add more RAM — the window is architecturally fixed."
- Practical: "Your Layer 4 context from the lab was ~1,000 tokens. That's 0.5% of Claude's window. You have room for MUCH more context — entire runbooks, service catalogs, incident histories."
- Why it matters for agents: An agent that processes 100 tool calls fills its context window fast. Context management is the #1 skill.

**3. Inference Pipeline — Prefill and Decode** (~25 lines, per D-24 solid depth)
- What: Two-phase process. Phase 1 (Prefill): Process ALL input tokens in parallel — this is why more context doesn't proportionally slow things down. Phase 2 (Decode): Generate output tokens one at a time, each depending on all previous tokens.
- DevOps analogy: "Like a 2-phase deployment. Phase 1 (prefill) = load the entire state (parallel, fast). Phase 2 (decode) = process requests serially (sequential, slower). Prefill is like terraform plan (read everything). Decode is like terraform apply (execute step by step)."
- Why this matters: Input tokens are CHEAPER than output tokens because prefill parallelizes. Claude: $3/M input vs $15/M output. Design your context to be rich (cheap) and your requested output to be concise (expensive).
- Practical implication: "This is why structured output format requests ('respond in JSON with these fields') save money — they constrain decode length."

**4. Temperature** (~15 lines)
- What: Controls randomness in token selection. 0 = always pick the highest-probability token. 1 = sample broadly.
- DevOps analogy: "Like a load balancer strategy. Temperature 0 = always route to the best server (deterministic). Temperature 1 = random selection (creative). For incident response, you want temperature 0 (consistent). For brainstorming architecture, temperature 0.7+ (diverse ideas)."
- Practical: "In the lab, you used the default temperature. For production agent skills (runbook execution), set temperature to 0. For design exploration, raise it."

**5. Top-P and Top-K** (~15 lines)
- What: Vocabulary filtering during generation. Top-K = "only consider the K most likely next tokens." Top-P (nucleus sampling) = "consider tokens until cumulative probability reaches P."
- DevOps analogy: "Like admission control. Top-K = 'only allow the top N pods to be scheduled.' Top-P = 'keep scheduling pods until resource budget is 95% used.' Both limit the candidate pool differently."
- Practical: "You rarely need to tune these directly. Temperature is the main knob. But understanding them helps you debug when an agent produces unexpected vocabulary."

**6. Token Economics** (~20 lines, reinforces lab Part 3)
- What: The business model of AI. Input tokens (your context) cost less than output tokens (the response). Prices have dropped ~80% since 2024.
- Current pricing table (2026):
  - Claude Sonnet 4.6: $3/M input, $15/M output
  - Gemini 2.5 Flash: Free tier (500 req/day)
  - Groq (Llama 3.1 8B): Free tier (14,400 req/day)
- Key insight: "Context engineering is cost engineering. Rich input context ($3/M) produces concise, accurate output ($15/M). Thin context produces long, wandering output that costs more and is less useful."
- Link back to the lab: "You calculated this in Part 3. Layer 4 costs 7x Layer 1 but the quality justifies it for critical operations."

**2. Context Engineering Philosophy (MOD1-06)** (~50 lines)
This is THE core message of the course. Frame it clearly:

- "Context engineering is NOT prompt engineering." Prompt engineering = clever phrasing to trick the model. Context engineering = giving the model the right information to do its job. The difference: "Prompt engineering asks 'how do I phrase this?' Context engineering asks 'what does the model need to know?'"
- The Anthropic framing: Context engineering = "the art of providing the right information, in the right format, at the right time." (Reference: Anthropic engineering blog on effective context engineering)
- Why DevOps people are ALREADY good at this: "You write runbooks. You structure Ansible playbooks. You define Terraform modules. You write Dockerfiles. All of these are forms of context engineering — structured knowledge that enables automation."
- The 4 layers from the lab, reframed as a pattern:
  1. Task definition (what to do)
  2. Role/expertise context (who is doing it)
  3. System context (where it's happening)
  4. Procedural context (how to do it — the runbook)
- "This pattern applies everywhere: Kubernetes troubleshooting, cost optimization, deployment validation, security auditing. The SKILL.md files you'll write in Module 7 ARE context engineering artifacts."

**3. What Context Engineering Looks Like in Practice** (~20 lines)
Quick reference showing how the same 4-layer pattern applies to different DevOps scenarios:
- Alarm triage (Module 1 lab)
- Cost anomaly analysis (Module 2)
- Deployment validation (Module 5)
- Infrastructure generation (Module 6)
For each: one-line example of what each context layer contains.

**Question 1: Tokenization**
"A CloudWatch alarm JSON payload is 800 characters. Approximately how many tokens is this?"
A) 80 tokens
B) 200 tokens (CORRECT — rough rule: 1 token ≈ 4 characters for English; JSON is slightly more token-dense)
C) 800 tokens
D) 2,400 tokens
Explanation: "Tokens are subword units, roughly 3-4 characters each for English text. JSON syntax characters ({, }, :, ",) each tend to be individual tokens, making JSON slightly more expensive than prose."

**Question 2: Context Window (conceptual)**
"Why is context window size the #1 constraint for AI agents?"
A) Larger windows cost more money
B) The model can only process a fixed amount of text at once — agents that call many tools fill the window quickly (CORRECT)
C) Larger windows make the model slower
D) Context windows limit the number of API calls
Explanation: "An agent processing 100 tool calls accumulates tool outputs in its context. At some point the window fills and the agent loses earlier context — like an OOM-killed container."

**Question 3: Inference Pipeline**
"In the inference pipeline, why are input tokens cheaper than output tokens?"
A) Input tokens are smaller
B) Input tokens are processed in parallel (prefill), while output tokens are generated one at a time (decode) (CORRECT)
C) Input tokens don't use GPU resources
D) Output tokens require more storage
Explanation: "Prefill processes all input tokens simultaneously — like loading a container image. Decode generates tokens sequentially — like processing requests. Parallel work is more efficient, hence cheaper."

**Question 4: Context Engineering vs Prompt Engineering**
"What is the key difference between context engineering and prompt engineering?"
A) Context engineering uses longer prompts
B) Context engineering focuses on WHAT information the model needs, not HOW to phrase the request (CORRECT)
C) Prompt engineering is more advanced
D) Context engineering only works with Claude
Explanation: "Prompt engineering optimizes phrasing. Context engineering provides the right domain knowledge, system state, and procedural context. The quality improvement in your lab came from adding information, not from clever wording."

**Question 5: Lab Application**
"In the Module 1 lab, which context layer produced the biggest quality improvement?"
A) Layer 1 → Layer 2 (adding SRE role)
B) Layer 2 → Layer 3 (adding infrastructure topology) (CORRECT — this is where generic becomes specific)
C) Layer 3 → Layer 4 (adding runbook)
D) All layers improved equally
Explanation: "Layer 3 (infrastructure topology) is where the response becomes specific to YOUR system. The model stops guessing and starts reasoning about your actual infrastructure. This is the inflection point where context engineering pays off."

**Question 6: Token Economics**
"At $3/M input tokens, what does it cost to analyze 500 CloudWatch alarms per day with Layer 4 context (~1,000 tokens each)?"
A) $0.15/day
B) $1.50/day (CORRECT — 500 x 1,000 = 500K tokens = $1.50 at $3/M)
C) $15.00/day
D) $150.00/day
Explanation: "500 alarms x 1,000 tokens = 500,000 tokens. At $3 per million input tokens: 0.5M x $3 = $1.50. Compare to the human cost of manual triage."

**Question 7: AI Spectrum**
"A system that autonomously detects a failing pod, diagnoses the root cause using kubectl and logs, and restarts the service — which level of the AI spectrum is this?"
A) Chat
B) Copilot
C) Agent (CORRECT — autonomous task execution with tool use)
D) Squad
Explanation: "This is a single agent performing observe-think-act autonomously with tools. A Squad would involve multiple agents coordinating — one diagnosing, one remediating, one verifying."
