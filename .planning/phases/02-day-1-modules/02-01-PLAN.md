**Structure the LAB.mdx in 3 parts:**

**Lab Header:**
- Duration: 60 minutes
- Deliverable: "A context template that produces expert-level CloudWatch alarm analysis"
- What you need: Claude Code or Crush (per D-22 — participants interact directly, no scripts)
- Data: `infrastructure/mock-data/cloudwatch/describe-alarms-anomaly.json` (from repo root). Include the FULL JSON inline in a collapsible `<details>` block as fallback so participants don't need to locate the file. Per D-21, add note: "If you have real CloudWatch alarms, use your own data instead."

**Part 1 — Progressive Context Engineering (MOD1-01 + MOD1-02, 35 minutes):**

Progression through 4 layers on the SAME alarm data (per D-19):

**Layer 1 — Bare prompt:**
Instructions: "Open Claude Code (or Crush). Paste the alarm JSON and ask: 'Analyze this CloudWatch alarm.' Save the output."
Expected result description: "Generic, vague analysis. No operational specificity. Likely misses the significance of the CPU threshold."

**Layer 2 — Add SRE role context:**
Instructions: "Now add role context before the alarm data." Provide the exact text:
```
You are an experienced SRE on a production e-commerce platform.
Your job is to diagnose CloudWatch alarms and recommend immediate actions.
Think in terms of: incident severity, customer impact, MTTR.
```
Expected result description: "More focused. Uses SRE vocabulary. Has severity framing. But still guessing about your specific infrastructure."

**Layer 3 — Add infrastructure topology:**
Instructions: "Now add infrastructure context." Provide the exact text:
```
Infrastructure context:
- i-0abc123def456001 is the catalog-api EC2 instance (t3.large)
- It serves the product catalog for 50K daily active users
- CPU typically runs at 60-65% during peak hours (09:00-21:00 UTC)
- It communicates with RDS PostgreSQL (db.t3.medium, max 100 connections)
- SNS alerts go to ops-alerts → PagerDuty → on-call rotation
```
Expected result description: "Specific to YOUR system. Mentions the catalog-api by name. Flags that 85% CPU is 20+ points above normal. May identify RDS connection pool as potential bottleneck."

**Layer 4 — Add runbook context:**
Instructions: "Now add your team's runbook." Provide the exact text:
```
SRE runbook — HighCPUUtilization response:
1. Check: Is this a known traffic spike? (check ALB request count)
2. Check: Is there a runaway process? (aws ssm send-command -- ps aux)
3. Check: Was there a recent deployment? (check CodeDeploy deployment history)
4. If traffic spike: scale out (aws autoscaling set-desired-capacity)
5. If runaway process: isolate and restart (aws ec2 reboot-instances after snapshotting logs)
6. Escalate if: CPU > 90% for > 10 minutes with no identified cause
7. Document: all findings in incident ticket before closing

Decision tree threshold: If StateValue=ALARM AND duration > 15 min, wake on-call.
```
Expected result description: "Expert-level. Follows your runbook's decision tree. Checks items in order. Produces a structured incident response plan. This is what context engineering gives you."

After each layer, include a **"What changed?"** reflection prompt asking participants to note the specific improvements they observed.

**Side-by-side comparison (per D-20):**
After all 4 layers, present a markdown table template for participants to fill in:

| Aspect | Layer 1 (Bare) | Layer 2 (Role) | Layer 3 (Topology) | Layer 4 (Runbook) |
|--------|---------------|----------------|--------------------|--------------------|
| Severity assessment | | | | |
| Specific to your infra? | | | | |
| Actionable next steps? | | | | |
| Would you trust this at 3am? | | | | |

Include a discussion callout: "This is context engineering. You didn't write a cleverer prompt. You gave the AI the same context an experienced SRE carries in their head. The AI's intelligence didn't change — the context did."

**Part 2 — Context Architecture Exercise (extension of MOD1-02, 10 minutes):**
Participants design a context template for a DIFFERENT alarm scenario. Give them `describe-alarms-clean.json` (the non-alarming state) and ask: "What context layers would you add for a cost anomaly alert from Cost Explorer? Draft 4 layers." This reinforces the pattern without providing the answer.

**Part 3 — Token Economics (MOD1-03, 15 minutes, per D-23):**

Present the cost estimation table (from RESEARCH.md Pattern 5):

| Layer | Context Added | Approx Tokens | Claude Sonnet 4.6 Cost* | Quality |
|-------|--------------|---------------|------------------------|---------|
| 1 — Bare prompt | Alarm JSON only | ~150 | $0.00045 | Generic |
| 2 — SRE role | + Role + instructions | ~350 | $0.00105 | Focused |
| 3 — Topology | + Instance/service context | ~600 | $0.00180 | Specific |
| 4 — Runbook | + Decision tree | ~1,000 | $0.00300 | Expert |

*At $3/M input tokens (Claude Sonnet 4.6, 2026 pricing).

Exercise: Have participants calculate:
- "If your team processes 500 alarms/day at Layer 4: $0.003 x 500 = $1.50/day = ~$45/month"
- "Compare to: one SRE spending 5 minutes per alarm = 500 x 5 = 2,500 minutes = ~42 hours/day (impossible without AI)"
- Discussion: "When is Layer 4 worth 7x the cost of Layer 1? When is Layer 2 sufficient?"
- Free tier framing: "Gemini 2.5 Flash free tier gives you 500 requests/day — enough for Layer 4 on all 500 alarms at zero cost. Token economics increasingly favor quality."

Include a callout about context window limits: Layer 4 at ~1,000 tokens is tiny compared to Claude's 200K context window. Real production contexts can include entire runbooks, service catalogs, and incident histories.

**Starter files (course-site/docs/module-01-foundations/lab/starter/):**

Create 4 markdown files that participants can copy-paste:

`context-layer-1.md`: Just the instruction "Analyze this CloudWatch alarm:" followed by a note to paste the alarm JSON below.

`context-layer-2.md`: The SRE role context text from Layer 2 above, followed by "Analyze this CloudWatch alarm:" and a paste placeholder.

`context-layer-3.md`: Layer 2 content + infrastructure topology from Layer 3, followed by "Analyze this CloudWatch alarm:" and paste placeholder.

`context-layer-4.md`: Everything from Layer 3 + runbook from Layer 4, followed by "Analyze this CloudWatch alarm:" and paste placeholder.

Each starter file has a comment at the top: "# Context Layer N — Copy this entire file, then paste your alarm JSON at the bottom"
