# Module 7 Lab: Write a Kubernetes Pod Health SKILL.md (Track C)

**Duration:** 60 minutes
**Track:** C — Kubernetes Health & Self-Healing
**Outcome:** A complete `SKILL.md` that diagnoses Kubernetes pod failures and passes the Track C rubric quality gate

:::important Track C commitment
This lab and the rest of your course work (Modules 8, 10, and beyond) use Track C.
The skill you write here is the skill you will attach to your Track C agent profile
in Module 8. Do not mix `kubectl` commands with `aws` or `psql` commands — cross-track
contamination is a Tier 1 rubric failure.
:::

## Step 1: Metadata — Skill Identity (5 min)

**Concept:** A skill is a named, versioned runbook. The frontmatter is its identity card.
It tells Hermes when to surface this skill and what domain it belongs to.

**What's visible in your starter file:** The YAML frontmatter block at the top.

**Your task:** Fill in every `[placeholder]` in the frontmatter:

- `name`: kebab-case, describes what the skill does. Examples: `k8s-pod-crashloop-diagnosis`, `k8s-pod-health-check`, `sre-k8s-pod-health`
- `description`: one sentence, action verb first, includes: what it does + Kubernetes resource + when to trigger
- `compatibility`: `"kubectl 1.28+, KIND v0.31+, HERMES_LAB_MODE=mock|live"`
- `metadata.hermes.category`: `sre`
- `metadata.hermes.tags`: 3-5 relevant tags from `[kubernetes, sre, pod-health, kubectl, k8s, diagnosis, incidents, crashloop, oomkilled]`

**Check your work:**

```bash
grep -c '\[' /tmp/my-k8s-skill.md
```

Result must show no `[placeholders]` remaining in the frontmatter section.

## Step 2: When to Use — Trigger Conditions (8 min)

**Concept:** Skills activate on SPECIFIC, OBSERVABLE conditions — not vague descriptions.
"When a pod is unhealthy" is wrong. "When a pod's `status.containerStatuses[].state.waiting.reason`
equals `ImagePullBackOff`" is right. If the trigger is vague, the agent will invoke the skill
for the wrong scenarios.

**Reveal:** Add the `## When to Use` section to your skill file after the frontmatter.

**Your task:**

1. Name 3-5 specific trigger conditions for Track C. Use exact Kubernetes field names:
   - Pod `CrashLoopBackOff` with `restartCount > N`
   - Pod `ImagePullBackOff` / `ErrImagePull`
   - Container terminated with `reason == "OOMKilled"` and `exitCode == 137`
   - Pod `Pending` with `CreateContainerConfigError` (missing Secret/ConfigMap)
   - `kubectl describe pod` Events section contains `Liveness probe failed`
   - Service exists but `kubectl get endpoints` returns `<none>`

2. Add 2 "Do NOT use this skill for" anti-cases — out-of-scope scenarios your skill
   explicitly does not handle. Examples: PVC binding failures, RBAC/admission webhook
   errors, cluster autoscaler issues, network policy debugging, steady-state capacity
   planning.

**Reference:** The Track C solution file has a complete `## When to Use` example at the top.

## Step 3: Inputs — Parameterize Your Skill (7 min)

**Concept:** Skills are functions. Explicit inputs make skills reusable across environments.
A skill that hardcodes `namespace=default` cannot diagnose problems in `namespace=prod`
without editing.

**Reveal:** Add the `## Inputs` and `## Prerequisites` sections.

**Your task:**

1. Fill the Inputs table with every env var and parameter your skill uses
2. For each input: name, source (env var / user prompt), required (yes/no), description
3. ALWAYS include `HERMES_LAB_MODE` as an input (mock vs live mode routing)
4. List required tools with version numbers
5. Add a Track C mock mode setup block showing how to verify mock data files are accessible

**Required Track C inputs:**

| Input | Source | Required | Description |
|-------|--------|----------|-------------|
| `NAMESPACE` | env var | YES | Target Kubernetes namespace |
| `POD_NAME` | env var | NO | Specific pod to diagnose; if unset, scan all unhealthy pods |
| `KUBECONFIG` | env var | NO | Path to kubeconfig (default: `~/.kube/config`) |
| `HERMES_LAB_MODE` | env var | NO | `mock` or `live` (default: `live`) |
| `HERMES_LAB_SCENARIO` | env var | NO | Required only when `HERMES_LAB_MODE=mock` |

## Step 4: Phase 1 — Scripts Zone (10 min)

**Concept:** The Scripts Zone is deterministic. It contains only CLI commands and their expected
output. No prose decisions. No "if you see X...". Just: run this command, here is what success
looks like, here is what a problem looks like. The agent executes these commands and feeds the
output to Phase 2.

**Reveal:** Add `## Procedure` with `### Phase 1` content.

**Your task:**

1. Write 3-5 `kubectl` steps that collect all diagnostic data your skill needs
2. For EACH step: exact command (with env var references) + expected healthy output + expected degraded output
3. Use real Kubernetes API field names (camelCase for kubectl: `containerStatuses`, `state.waiting.reason`)
4. `HERMES_LAB_MODE` check: your `mock-kubectl` wrapper returns the same JSON structure as real kubectl — same field paths

**Track C Phase 1 starter commands:**

```bash
# Step 1: Pod inventory — broad scan with field-level details
kubectl get pods -n $NAMESPACE -o json
# Mock mode: reads from infrastructure/mock-data/kubernetes/${HERMES_LAB_SCENARIO}-get-pods.json
# Live mode: hits your real KIND cluster

# Step 2: Pod-specific deep-dive — events, container state, restart count
kubectl describe pod $POD_NAME -n $NAMESPACE
# Mock mode: reads from infrastructure/mock-data/kubernetes/${HERMES_LAB_SCENARIO}-describe.txt

# Step 3: Previous-instance logs (for CrashLoopBackOff diagnosis)
kubectl logs $POD_NAME -n $NAMESPACE --previous --tail=100
```

**Expected output (image-pull scenario, partial):**

```json
{
  "items": [{
    "status": {
      "containerStatuses": [{
        "state": {"waiting": {"reason": "ImagePullBackOff", "message": "Back-off pulling image..."}},
        "ready": false,
        "restartCount": 0
      }]
    },
    "spec": {
      "containers": [{"image": "nonexistent-registry.io/fake-app:v1.0.0"}]
    }
  }]
}
```

The exact JSON path your Phase 2 decision tree should reference is
`status.containerStatuses[].state.waiting.reason` — that's the field that distinguishes
`ImagePullBackOff` from `CrashLoopBackOff` from `CreateContainerConfigError`. Always cite
the path, never invent it.

**To exercise other scenarios:** swap `HERMES_LAB_SCENARIO=image-pull` for `crashloop2`,
`oom`, `liveness`, `missing-secret`, or `port-mismatch` in your shell. Each produces
different mock JSON shapes with different `state.waiting.reason` / `lastState.terminated.reason`
values that your skill needs to handle.

**Common mistake:** Including reasoning ("if `restartCount > 5`, do X") in Phase 1. Phase 1
is data collection only. Save reasoning for Phase 2.

## Step 5: Phase 2 — Agents Zone (12 min)

**Concept:** The Agents Zone is where reasoning happens. Decision trees must be numeric and
complete: every branch must end at a named diagnosis or escalation. "Investigate further" is
not a valid terminal. Vague conditions ("if the pod seems unhealthy") are Tier 1 rubric
failures.

**Reveal:** Add `### Phase 2` under `## Procedure`.

**Your task:**

1. Write a decision tree using the data from Phase 1
2. Every IF condition must reference a specific Kubernetes field: `state.waiting.reason == "OOMKilled"`, `restartCount > 5`, not "pod is unhealthy"
3. Every branch must end with: `Diagnosis = "NAMED_ROOT_CAUSE"` or `ESCALATE`
4. Include at least one ELSE branch (handles normal state)
5. Cover at least 3 of the 6 Track C failure modes

**Required format:**

```
IF status.containerStatuses[].state.waiting.reason == "ImagePullBackOff":
  THEN: Diagnosis = "IMAGE_PULL_FAILURE"
  EVIDENCE: spec.containers[].image value
  CONFIDENCE: High — kubectl directly reports the reason
ELSE IF lastState.terminated.reason == "OOMKilled" AND lastState.terminated.exitCode == 137:
  THEN: Diagnosis = "OOM_KILLED"
  EVIDENCE: lastState.terminated.finishedAt, spec.containers[].resources.limits.memory
  CONFIDENCE: High — kernel-level signal
ELSE:
  THEN: Diagnosis = "NO_ISSUE_FOUND"
```

**Common mistake:** Writing a Phase 2 step that runs a new `kubectl` command. Phase 2 interprets
existing data — it does not gather new data. If you need a new command, it goes in Phase 1.

## Step 6: Escalation Rules and NEVER DO (8 min)

**Concept:** Safety posture. Every skill must know when to stop and hand off to a human.
`NEVER DO` rules prevent the most catastrophic agent actions — they must be specific
commands, not abstract prohibitions ("never do anything dangerous" is not a NEVER DO rule).

**Reveal:** Add `## Escalation Rules` and `## NEVER DO`.

**Your task (Escalation Rules):**

1. Write 3-4 escalation triggers with specific, observable Kubernetes conditions
2. Each trigger: what condition, why it exceeds agent scope, what to hand off to human
3. Include the escalation handoff template (Subject, Findings, Evidence, Urgency)

**Track C escalation examples:**

- `restartCount > 10` across multiple pods in the same deployment (systemic issue)
- Node `NotReady` condition persists more than 2 minutes
- `OOMKilled` events across multiple namespaces (possible cluster-wide memory pressure)
- Any failure mode not in the six covered by this skill

**Your task (NEVER DO):**

Write 4-5 hard prohibitions — the most destructive things your Kubernetes agent could do.
Each prohibition: specific `kubectl` command + specific catastrophic outcome.

**Track C NEVER DO starter list:**

- NEVER execute `kubectl delete` (pod, deployment, any resource) — use case: prevents accidental removal
- NEVER execute `kubectl drain` — affects all workloads on a node, always escalate
- NEVER execute `kubectl cordon` without approval — prevents new pod scheduling
- NEVER modify resource limits/requests without an approved change request
- NEVER execute `kubectl exec`, `kubectl edit`, `kubectl patch`, or `kubectl apply` — this skill is read-only

## Step 7: Rollback and Verification (5 min)

**Concept:** Every mutation needs an undo path. Even read-only skills need a verification
checklist to confirm the diagnostic run was complete.

**Reveal:** Add `## Rollback Procedure` and `## Verification`.

**Your task (Rollback):**

Because this skill is read-only (Phase 3 mutations are escalated, not executed), the rollback
section should document: "This skill performs no mutations. All self-healing actions are
escalated for human execution. If a human executes a rollback, they should use the standard
`kubectl rollout undo deployment/<name>` pattern with the deployment name from Phase 1."

**Your task (Verification checklist):**

Add a checklist confirming:

- [ ] All Phase 1 commands ran successfully and returned data (not errors)
- [ ] Phase 2 decision tree reached a named diagnosis (not "investigate further")
- [ ] Evidence cited includes specific pod name, namespace, and Kubernetes field paths
- [ ] No write-verb `kubectl` commands were executed
- [ ] Escalation trigger conditions were checked
