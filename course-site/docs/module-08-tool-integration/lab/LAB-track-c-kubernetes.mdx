# Module 8 Lab: Wire Tools to Your Track C Agent (Kubernetes)

**Duration:** 75 minutes
**Track:** C — Kubernetes Health & Self-Healing
**Prerequisite:** Module 7 Track C lab complete (you authored `my-track-c-skill.md`)
**Outcome:** A running `track-c` Hermes profile with Kiran's identity, the Anthropic model, and your Module 7 skill attached — tested end-to-end against mock pod scenarios

:::tip
By the end of this lab you will run `hermes -p track-c chat` and talk to an agent you built:
Kiran's behavior rules from the reference, your Module 7 skill, Anthropic Claude Haiku 4.5
as the brain.
:::

:::info Philosophy: examine + copy, not write from scratch
This lab uses a different approach from the unified Module 8 lab. Instead of having you
author `SOUL.md` and `config.yaml` from blank starters with `[placeholder]` fields, you will
**examine** the production-grade reference files for Track C, understand what each section
does, then **copy** them directly into your profile. The learning value in Module 8 is
understanding *what lives in a Hermes profile*, not word-smithing identity prose. You can
customize the agent name or add your own rules later if you want.
:::

### Track C lab environment (mock mode — default path)

Track C ships a `mock-kubectl` wrapper and six baked pod failure scenarios. Set these before
launching `hermes chat`:

:::important Prerequisite: one-time `~/.bash_profile` alias setup
If you haven't already, follow [Setup → Step 5: Lab Wrapper Aliases](../../setup.mdx#step-5-lab-wrapper-aliases-one-time-setup)
to add the one-time alias block to your `~/.bash_profile`. Hermes spawns
`bash -lic` for tool execution, which rebuilds `PATH` during login-shell startup
and demotes any wrapper dir you set in `PATH`. The alias block survives that
startup and correctly routes `kubectl`/`aws`/`psql` through the mock wrapper.
:::

```bash
# Required: tells the ~/.bash_profile alias block where the wrappers live
export HERMES_LAB_WRAPPERS="$(pwd)/infrastructure/wrappers"

export HERMES_LAB_MODE=mock
export HERMES_LAB_SCENARIO=clean              # or: crashloop2 | oom | image-pull | liveness | missing-secret | port-mismatch
export HERMES_LAB_TRACK=track-c
export MOCK_DATA_DIR="$(pwd)/infrastructure/mock-data"

# Optional — helps if you run kubectl DIRECTLY in this outer shell (not needed for Hermes's subshell).
export PATH="$HERMES_LAB_WRAPPERS:$PATH"

# Verify the wrapper script exists
ls "$HERMES_LAB_WRAPPERS/mock-kubectl"
# Expected: <course-dir>/infrastructure/wrappers/mock-kubectl
```

:::note Live mode (optional — if you have KIND running)
If you have a KIND cluster and want your agent to exercise a real cluster, set
`export HERMES_LAB_MODE=live` instead. The wrappers auto-exec the real `kubectl` binary when
`HERMES_LAB_MODE != "mock"`. See the [Module 8 Reference](../reading/reference.mdx) §4 for
the wrapper implementation details. The rest of this lab works identically in either mode —
live-specific notes are marked **[LIVE MODE]**.
:::

## What You're Building

A Hermes profile is a directory. When you run `hermes -p track-c`, Hermes uses that
directory as its home — reading the identity from `SOUL.md`, the config from `config.yaml`,
and the skills from the `skills/` subdirectory.

**Final profile structure you'll create:**

```
~/.hermes/profiles/track-c/
├── SOUL.md                          ← Kiran's identity (examine + copy in Step 3)
├── config.yaml                      ← Model + approvals + wrapper_allowlist (examine + copy in Step 4)
├── .env                             ← Your Anthropic API key (Step 4)
└── skills/
    └── <your-skill-name>/
        └── SKILL.md                 ← Your Module 7 skill (attach in Step 6)
```

**Reference files you will examine and copy:**

| Source in repo | Destination in profile |
|---|---|
| `agents/track-c-kubernetes/SOUL.md` | `~/.hermes/profiles/track-c/SOUL.md` |
| `agents/track-c-kubernetes/config.yaml` | `~/.hermes/profiles/track-c/config.yaml` |
| `modules/module-07-skills/my-track-c-skill.md` | `~/.hermes/profiles/track-c/skills/<your-skill>/SKILL.md` |

## Step 3: Examine and Install SOUL.md (15 min)

**Concept:** Your agent's `SOUL.md` is its identity. Hermes reads it at startup and uses it
as the agent's entire persona — replacing the generic "Hermes Agent" default. For Track C,
the reference identity is "Kiran" — a Kubernetes operations agent with specific behavior
rules, escalation policy, and NEVER DO constraints.

### Step 3a: Read the reference SOUL.md

```bash
cat agents/track-c-kubernetes/SOUL.md
```

Walk through each section as you read it:

| Section | What it does | Why it matters |
|---|---|---|
| **Title + Role + Domain + Scope** | Names the agent (Kiran) and declares its remit (Kubernetes, read-only diagnosis) | Gives the LLM a frame — Kiran is not a database agent, not a FinOps agent |
| **Identity** | First-person persona: "You are Kiran, a Kubernetes operations agent for platform engineering teams..." | Sets tone, authority, and domain vocabulary the LLM will inhabit |
| **Behavior Rules** | Concrete rules: detect `HERMES_LAB_MODE` as first tool call; always run fresh `kubectl` commands; cite exact pod name + namespace + failure reason | These are the rules Hermes injects into every turn — the LLM follows them literally |
| **NEVER rules** | Hard prohibitions: `kubectl delete`, `kubectl drain`, `kubectl cordon`, `kubectl exec/edit/patch/apply` | Behavioral safety — Track C uses SOUL.md NEVER rules instead of Hermes `DANGEROUS_PATTERNS` because `kubectl delete` is not pattern-matched by Hermes |
| **Escalation Policy** | Specific conditions where Kiran stops and hands off: confirmed failure modes, node NotReady > 2 min, multi-namespace OOMKilled | Forces the agent to know its limits |

**Key thing to notice:** The reference Kiran `SOUL.md` has **zero `[placeholders]`**. It's
a finished identity. You do not need to fill anything in.

### Step 3b: Copy the reference SOUL.md into your profile

```bash

```

## Step 4: Examine and Install config.yaml (15 min)

**Concept:** Your `config.yaml` controls the model (the "brain"), which tools the agent has
access to, how it handles potentially dangerous commands, and which `kubectl` subcommands
the Track C wrappers allow in lab environments.

### Step 4a: Read the reference config.yaml

```bash
cat agents/track-c-kubernetes/config.yaml
```

Walk through the key sections:

| Section | What it controls |
|---|---|
| `model.default` / `model.provider` | Which LLM answers the agent. Track C default is `anthropic/claude-haiku-4-5` via the `Anthropic` provider. |
| `platform_toolsets.cli` | Which Hermes tool families the agent can use: `[terminal, file, web, skills]` (L2 Advisory — the agent can run shell commands, read files, fetch URLs, and load attached skills) |
| `approvals.mode: manual` | Every command matching Hermes `DANGEROUS_PATTERNS` pauses for your approval |
| `approvals.timeout: 300` | 5-minute window to approve/deny before the command is auto-rejected — required for multi-step lab flows |
| `wrapper_allowlist.kubectl` | The list of `kubectl` subcommands the Track C `mock-kubectl` wrapper allows under `HERMES_LAB_GOVERNANCE=L2`. Track C allows read-only verbs: `get pods`, `describe pod`, `logs`, `top pods`, etc. Anything outside this list is rejected at the wrapper layer. |
| `agent.max_turns` / `agent.verbose` | Conversation loop limits |

### Step 4b: Copy the reference config.yaml into your profile

```bash
cp agents/track-c-kubernetes/config.yaml ~/.hermes/profiles/track-c/config.yaml
```

### Step 4c: Set up your Anthropic API key

The default Track C model is `anthropic/claude-haiku-4-5` via the Anthropic provider. You
need an Anthropic API token, which Claude Code can mint for you (no credit card required
if you already have a Claude Pro/Team subscription).

```bash
# Get a short-lived Anthropic API token via Claude Code
claude setup-token

# Export it as an environment variable (paste the token it printed)
export ANTHROPIC_TOKEN=<your-token>

# Add it to the track-c profile's .env file
echo "ANTHROPIC_API_KEY=$ANTHROPIC_TOKEN" >> ~/.hermes/profiles/track-c/.env
```

:::tip Alternate provider setup
If you want to use Google Gemini, OpenRouter, or Groq instead of Anthropic, see the full
walkthrough in `setup/llm-access.md`. You would change `model.default` and `model.provider`
in the copied `config.yaml` and add the matching API key to `.env`. The rest of this lab
works identically.
:::

## Step 5: Run Your Agent — No Skills Yet (8 min)

**This step is intentional.** Run your agent before attaching any skill. The goal is to see
that the profile IS the identity, even without skills — Kiran's behavior rules and safety
constraints are already in effect.

### Step 5a: Confirm your env vars BEFORE launching

The Hermes process inherits environment variables **from the shell that launches it** — and
only at launch time. Once `hermes chat` is running, env var changes you make in the same
terminal do NOT propagate into the agent's process. This matters because the lab is designed
around `HERMES_LAB_MODE`, `HERMES_LAB_SCENARIO`, and (later) `HERMES_LAB_GOVERNANCE` — get
them wrong before you launch and your agent will run in the wrong mode for the entire
session.

```bash
# Confirm what mode you're in (check ALL the lab env vars)
echo "MODE=$HERMES_LAB_MODE  SCENARIO=$HERMES_LAB_SCENARIO  TRACK=$HERMES_LAB_TRACK"
# Expected: MODE=mock  SCENARIO=clean  TRACK=track-c

# Confirm the kubectl wrapper is in PATH (symlink to mock-kubectl)
which kubectl
# Expected: <course-dir>/infrastructure/wrappers/kubectl
# Note: the wrapper path is correct in BOTH mock and live mode — the wrapper
# internally execs the real kubectl binary when HERMES_LAB_MODE=live.
# If you see /usr/local/bin/kubectl, your PATH export did not take effect.

# If anything's wrong, re-run the export block from Prerequisites BEFORE launching
```

:::tip Switching mock ↔ live after `hermes chat` is already running
The wrapper scripts (`mock-kubectl`) are tiny bash routers that re-read `HERMES_LAB_MODE` on
EVERY invocation, not at Hermes startup. If you `export HERMES_LAB_MODE=live` in the
**original shell** (the one that launched `hermes chat`), the wrapper child processes inherit
the new value on their next invocation — even though Hermes itself still thinks
`HERMES_LAB_MODE=mock`. The wrapper layer is what actually decides mock vs live.

**This does NOT work** if you try to change `HERMES_LAB_MODE` in the same terminal blocked
by the `hermes chat` REPL — you can't run shell commands until you exit. Open a second
terminal if you want to flip modes mid-session.
:::

### Step 5b: Launch the agent

```bash
hermes -p track-c chat
```

**Ask your agent:**

```
Who are you and what is your operating mode?
```

**Expected:** Kiran introduces itself as a Kubernetes operations agent, reports the
`HERMES_LAB_MODE` value (MOCK), and describes its scope: detecting pod failures, OOM events,
and node pressure — then recommending self-healing actions with approval. This comes
entirely from the `SOUL.md` you copied in Step 3 — no skills are attached yet.

**To verify the active mode from inside the chat:**

```

[ MOCK MODE ] banner appeared.
```

- **Mock mode confirmed:** agent reports the `[ MOCK MODE ]` banner and returns

- **[LIVE MODE] confirmed:** no banner; agent returns whatever pods are actually in your

If the identity is wrong (the agent says "I am Hermes Agent" instead of introducing as
Kiran), check that `~/.hermes/profiles/track-c/SOUL.md` exists and contains the
Kiran identity from Step 3.

Exit the chat session: type `exit` or Ctrl+C.

## Step 8: Test a Safety Boundary (12 min)

Hermes's approval gate catches commands matching `DANGEROUS_PATTERNS` in
`tools/approval.py`. You configured `approvals.mode: manual` (via the copied
`config.yaml`) in Step 4. Now you'll trigger it.

:::note Track C safety is split between two mechanisms
- **Hermes approval gate (`DANGEROUS_PATTERNS`):** catches shell-level destructive commands
  like `rm -rf`, `git reset --hard`, etc. — these fire an approval prompt.
- **SOUL.md NEVER rules:** catch Kubernetes-specific destructive commands like `kubectl delete`,
  `kubectl drain`, `kubectl cordon`. These are NOT in Hermes `DANGEROUS_PATTERNS` — the agent
  refuses them verbally based on behavior rules.

You will test both in Module 10 Track C. For now, you'll trigger the Hermes approval gate
with a non-kubectl command.
:::

**Test the Hermes approval gate:**

```
Try running: rm -rf /tmp/test-dir
```

**Expected:** The approval gate fires for "recursive delete". Type `deny` to cancel.

**What you just tested:** The approval gate works. Your agent cannot execute a flagged
command without your explicit approval. This is governance L2 in action.

**Exit the chat session.**
