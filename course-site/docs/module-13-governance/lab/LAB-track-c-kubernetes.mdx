# Module 13 Lab: Governance for Kiran — Approvals, Maturity Levels, and Audit Trails (Track C)

**Duration:** 90 minutes (60 min guided + 30 min free explore)
**Track:** C — Kubernetes Health & Self-Healing
**Prerequisite:** Module 10 Track C complete (`~/.hermes/profiles/track-c/` exists with Kiran's `SOUL.md`, `config.yaml`, and the `sre-k8s-pod-health` skill)
**Outcome:** Kiran configured at L3 governance, approval behavior observable in action, session audit trail readable via `sqlite3`, and a clear mental model of why Track C's dangerous commands are governed differently from Track A's.

:::tip
Governance is not about trust — it's about observability and control surfaces. L1 through L4 is a
spectrum from "human does everything" to "agent does routine work autonomously." Today you walk Kiran
from L1 to L4 and see exactly what each level changes. The diff between levels IS the governance
decision.
:::

:::important Why Track C is the clearest governance story
Track C is the lab where the mechanical-vs-behavioral safety split is most visible. The three
most destructive Kubernetes commands — `kubectl delete`, `kubectl drain`, `kubectl cordon` —
are **NOT** in Hermes `DANGEROUS_PATTERNS`. They are governed **only** by Kiran's `SOUL.md` NEVER
rules and (at L2+) by the `wrapper_allowlist.kubectl` enforcement layer. On Track A, SQL DROP
has three layers of defense; on Track C, the three layers look completely different. You will
see this play out in Step 5.
:::

### Step 5a: The SOUL.md refusal (no approval gate)

Ask Kiran something destructive at the `kubectl` level:

```
Delete pod api-deployment-def456 in the app namespace
```

**Expected:** Kiran **refuses verbally**. Its response will cite its SOUL.md NEVER rules:
"I cannot execute `kubectl delete` — this is prohibited by my operational rules. Deleting pods
can cause service disruption and data loss. Please have a human operator run this command with
explicit change approval."

**Critical observation: no approval gate fires.** No "[o]nce / [s]ession / [a]lways / [d]eny"
prompt appears. Kiran refused at Layer 3 (behavioral — SOUL.md NEVER rules) **before** forming
a terminal command. The Hermes approval gate (Layer 2 — DANGEROUS_PATTERNS) is never reached.

### Step 5b: The DANGEROUS_PATTERNS gate (approval prompt)

Now ask Kiran to do something destructive at the **shell** level:

```
Clean up the /tmp/test-logs directory recursively so I can free up space
```

**Expected:** Kiran will propose running `rm -rf /tmp/test-logs` or `rm -r /tmp/test-logs`.
That command matches `rm -r` in Hermes `DANGEROUS_PATTERNS`. The CLI will **pause** and show:

```
  WARNING  DANGEROUS COMMAND: recursive delete
      rm -rf /tmp/test-logs

      [o]nce  |  [s]ession  |  [a]lways  |  [d]eny

      Choice [o/s/a/D]:
```

Type `d` and press Enter to deny.

Exit the session: type `exit`

:::info CRITICAL TEACHING MOMENT — the split safety model for Track C

You just saw two different safety mechanisms, both active at L2:

| Command Kiran tried | Safety layer that caught it | How it fired |
|---|---|---|
| `kubectl delete pod api-deployment-def456` | **Layer 3 — SOUL.md NEVER rule** (behavioral) | Kiran refused to even propose the command |
| `rm -rf /tmp/test-logs` | **Layer 2 — DANGEROUS_PATTERNS** (mechanical) | Hermes paused the tool call and asked you to approve/deny |

**Why the split matters for Track C:**

Hermes `DANGEROUS_PATTERNS` is a hardcoded regex list in `tools/approval.py`. It contains shell
classics like `rm -r`, `dd if=`, `curl | bash`, `chmod 777`, `kill -9 -1`, and SQL mutations
like `DROP TABLE` and `DELETE FROM`. But it does **NOT** contain:

- `kubectl delete` (any resource)
- `kubectl drain`
- `kubectl cordon`
- `kubectl uncordon`
- `kubectl taint`
- `kubectl exec` / `edit` / `patch`

Kubernetes verbs are not shell patterns — they are subcommands of a binary that Hermes cannot
pattern-match safely (too many false positives would fire on reading commands). So Kubernetes
destructive commands must be protected by **behavioral** safety (SOUL.md NEVER rules), not
**mechanical** safety (DANGEROUS_PATTERNS).

This is why Kiran's SOUL.md is load-bearing for Track C. If you weaken Kiran's SOUL.md NEVER
rules — for example, by removing "NEVER execute `kubectl delete`" — then `kubectl delete pod
foo` will run silently at L2 with no approval prompt. Hermes has no idea it's dangerous.
Your safety disappears the moment SOUL.md drifts.

At L2 in Track C you have **two** protection layers (SOUL.md NEVER + wrapper_allowlist).
Phase 7 added the wrapper_allowlist specifically to give Track C (and Track B) a mechanical
layer that DANGEROUS_PATTERNS doesn't provide. You will see this layer fire in Step 10.
:::

## Step 6: Diff L2 to L3 — Smart Approval + wrapper_allowlist Expansion (5 min)

```bash
diff governance/governance-L2.yaml governance/governance-L3.yaml
```

**Expected output:**

```diff
< approvals:
<   mode: manual            # Every DANGEROUS_PATTERNS match requires human approval
---
> approvals:
>   mode: smart             # Auxiliary LLM auto-approves low-risk flagged commands
11a12,18
>   # L3 additions: rollout history, diff, explain
>   kubectl adds: rollout history, rollout status, diff, explain
>   aws adds: logs describe-, logs get-log-events, iam get-, iam list-
>   psql adds: EXPLAIN ANALYZE, DELETE FROM, UPDATE
```

Two changes: `approvals.mode` flips from `manual` to `smart`, AND `wrapper_allowlist.kubectl`
gains four investigation commands — `rollout history`, `rollout status`, `diff`, `explain`.
These are still non-destructive but reveal more cluster state than the L2 baseline.

:::info Teaching moment: the wrapper_allowlist diff

The `wrapper_allowlist` additions at L3 are the concrete form of "trust escalation." At L2
Kiran runs read-only pod-inspection commands. At L3 it gains investigation commands that
reveal history and state but still cannot mutate anything.

Specifically for Track C:
- `kubectl rollout history deployment/foo` — reveals deployment revision history
- `kubectl rollout status deployment/foo` — shows in-progress rollout state
- `kubectl diff -f <manifest>` — compares a manifest to live state (read-only; does not apply)
- `kubectl explain pod.spec.containers` — documents API fields

The diff between L2 and L3 is not just `mode: manual` → `mode: smart`. It is also the
`wrapper_allowlist.kubectl` expansion from diagnostic reads to investigation commands. Both
changes happen together — you cannot have smart approval without also granting the
investigation commands that smart approval was designed for.
:::

:::info How smart approval works

When `mode: smart`, Hermes sends flagged commands to a secondary (auxiliary) LLM for risk
assessment before interrupting the user. The auxiliary LLM responds with:
- `APPROVE` — command is clearly safe (e.g., `EXPLAIN SELECT ...` flagged as SQL but harmless)
- `DENY` — command is genuinely dangerous (e.g., `rm -rf /`)
- `ESCALATE` — uncertain, escalate to human

Low-risk `DANGEROUS_PATTERNS` false positives (diagnostic reads that happen to contain a
flagged keyword — e.g., the word "delete" appearing in a log message being `cat`-ed) auto-approve
at L3. Genuinely dangerous commands still pause for human approval.

**For Track C this matters less** because Hermes `DANGEROUS_PATTERNS` rarely fires on kubectl
commands in the first place. Smart approval mainly reduces friction when Kiran is inspecting
files or logs that happen to contain dangerous-looking strings (e.g., a pod's environment
variable named `DROP_TABLE_IF_EXISTS=false`).
:::

execute reads and investigations, propose self-healing actions as kubectl commands in its
response — but cannot unilaterally execute those mutations.

## Step 8: Read Your Session Audit Trail (10 min)

Every command Kiran attempts — and every approval decision — is recorded in the Hermes
session database. This is the audit trail a security review would ask to see.

**Find the session database:**

```bash
ls ~/.hermes/state.db
# Expected: ~/.hermes/state.db
```

**Inspect recent sessions:**

```bash
hermes sessions list
```

Note the session ID from your most recent session (e.g., `a1b2c3d4`).

**Query the audit trail with sqlite3:**

Open the database:

```bash
sqlite3 ~/.hermes/state.db
```

Inside sqlite3, run these queries:

```sql
-- List recent sessions
SELECT id, datetime(started_at, 'unixepoch', 'localtime') as started, title
FROM sessions
ORDER BY started_at DESC
LIMIT 5;
```

```sql
-- Show all terminal tool calls in the most recent session
-- (replace SESSION_ID with the ID from hermes sessions list)
SELECT
    datetime(timestamp, 'unixepoch', 'localtime') as time,
    role,
    tool_name,
    substr(content, 1, 200) as content_preview
FROM messages
WHERE session_id = 'SESSION_ID'
  AND (tool_name = 'terminal' OR role = 'tool')
ORDER BY timestamp ASC;
```

```sql
-- Find all the kubectl commands Kiran ran today
SELECT
    datetime(m.timestamp, 'unixepoch', 'localtime') as time,
    s.id as session_id,
    substr(m.content, 1, 300) as command_preview
FROM messages m
JOIN sessions s ON s.id = m.session_id
WHERE m.content LIKE '%kubectl %'
  AND m.role = 'tool'
  AND s.started_at > strftime('%s', 'now', '-1 day')
ORDER BY m.timestamp DESC
LIMIT 20;
```

```sql
-- Find refusal events (SOUL.md NEVER rule activations) in recent sessions
SELECT
    datetime(m.timestamp, 'unixepoch', 'localtime') as time,
    s.id as session_id,
    substr(m.content, 1, 300) as content_preview
FROM messages m
JOIN sessions s ON s.id = m.session_id
WHERE (m.content LIKE '%I cannot execute%'
   OR m.content LIKE '%NEVER rule%'
   OR m.content LIKE '%prohibited%')
ORDER BY m.timestamp DESC
LIMIT 10;
```

Exit sqlite3:

```sql
.quit
```

:::info What you just read

The `messages` table is the complete record of everything Kiran attempted. Tool-role messages
with `tool_name = 'terminal'` show every `kubectl`, `mock-kubectl`, or shell command the agent
ran (or tried to run).

For Track C specifically, two patterns matter:

1. **Executed kubectl commands** (`tool_name = 'terminal'`, content starts with `kubectl` or
   `mock-kubectl`): these are the commands that reached the wrapper and ran. Their exit codes
   and output are in subsequent tool-result messages.

2. **Refusal messages** (assistant-role messages containing "I cannot execute" or "NEVER rule"):
   these are the Layer 3 catches — Kiran refused to form the tool call in the first place.
   There's no corresponding tool message because no command was attempted.

A security reviewer cares about BOTH:
- What did Kiran run successfully?
- What did Kiran **want to run** but was refused at the behavioral layer?

The refusal log is evidence that SOUL.md is actively blocking intents — which is also evidence
that those intents are being formed in the first place. If you see Kiran refusing `kubectl
delete` repeatedly, that's a signal to review whether the prompts it's receiving are
appropriate for its scope.
:::

All three layers are active at L4 for Track C:
- **Layer 1**: wrapper_allowlist.kubectl (mechanical, course-local, Phase 7)
- **Layer 2**: DANGEROUS_PATTERNS (mechanical, Hermes-native — rarely fires for kubectl)
- **Layer 3**: SOUL.md NEVER rules (behavioral, identity-level)

L4 only widens Layer 1 slightly. Layers 2 and 3 are unchanged.

**Expected output:**

║           [ GOVERNANCE REJECTED ]                    ║
╠──────────────────────────────────────────────────────╣

:::info The three-layer defense model — Track C view
This is the teaching moment the whole course has been building to.

Your `kubectl delete` attempt just hit **two** of the three defense layers:

- **Layer 1 — wrapper_allowlist.kubectl (mechanical, Phase 7, course-local):** `kubectl delete`
  is not in `wrapper_allowlist.kubectl` at any governance level. The `mock-kubectl` wrapper
  rejected the command before it reached the real kubectl binary. This is the banner you just
  saw.

- **Layer 2 — DANGEROUS_PATTERNS (mechanical, Hermes-native):** DOES NOT FIRE for `kubectl
  delete`. This pattern is not in the Hermes regex list. If you had bypassed the wrapper (e.g.,
  by running `/usr/local/bin/kubectl delete pod foo` directly, bypassing PATH), Layer 2 would
  not have caught it. **This is why Track C depends on Layers 1 and 3.**

- **Layer 3 — SOUL.md NEVER rules (behavioral, identity-level):** Kiran has a NEVER rule
  refusing to execute `kubectl delete`. If Kiran were the one forming the tool call (rather
  than you typing it directly at the shell), Layer 3 would have refused before Layer 1 ever
  saw the command.

Contrast with Track A's `DROP TABLE`: all three layers fire for SQL DROP because DANGEROUS_PATTERNS
contains it as a hardcoded regex. Track C loses Layer 2 for its Kubernetes mutations — the
mechanical safety net is narrower by design. Phase 7 added Layer 1 (wrapper_allowlist) specifically
to strengthen Track C's defense, because SOUL.md alone (Layer 3) is a single point of failure.

**The takeaway:** when you evaluate an agent's governance posture, count the layers that apply
to the specific commands it will touch. Track A agents at L4 have 3 layers for destructive SQL.
Track C agents at L4 have 2 layers (1 + 3) for destructive kubectl, and even that depends on
SOUL.md staying intact. That asymmetry is the reason SOUL.md drift is a governance incident
for Track C and a minor finding for Track A.
:::

## Step 13: Review DANGEROUS_PATTERNS Relevance for Track C (5 min)

The full `DANGEROUS_PATTERNS` list is Hermes's mechanical safety contract. For Track C, it's

:::info What Track C actually hits

**Patterns Kiran might trigger (rare but possible):**
- `rm -r` / `rm --recursive` — if Kiran tries to clean up log files, tmp directories, or
  leftover kubeconfig bits during a diagnostic session. Likely scenario: you ask it to "clean

- `kubectl delete` (pod, deployment, any resource)

- `kubectl taint`
- `kubectl exec` / `edit` / `patch`
- `kubectl apply` (mutation, but not destructive — intentionally not in DANGEROUS_PATTERNS)
- `kubectl rollout undo` (mutation, but not destructive)

For all of these, your protection is:
1. **Layer 1**: `wrapper_allowlist.kubectl` (Phase 7, course-local) — only the explicitly listed
   prefixes pass through.
2. **Layer 3**: Kiran's SOUL.md NEVER rules — refuses to even form the intent for destructive
   verbs like delete, drain, cordon, exec.

**Both layers must hold for Track C to be safe.** Phase 7 added Layer 1 specifically because
Layer 3 alone was a single point of failure — if someone tampered with Kiran's SOUL.md (or
used a different profile name), SOUL.md NEVER rules wouldn't apply to the replacement profile.
Layer 1 is profile-independent: it's enforced by the wrapper binary regardless of which agent
invoked it.
:::
