# Concepts: Governance Triad and Maturity Levels

Your agent can diagnose, recommend, and act. The question is: should it? Governance is where you draw the lines — what actions it can take autonomously, what needs human sign-off, and what gets recorded for accountability.

---

## 1. The Governance Triad: DO × APPROVE × LOG

Every agent action falls into one of three categories:

**DO** — actions the agent can take autonomously, without any human approval.

**APPROVE** — actions the agent can propose but not execute until a designated approver confirms.

**LOG** — everything the agent does, regardless of category, recorded in an immutable audit trail.

**DevOps analogy:** The security triad (CIA — Confidentiality, Integrity, Availability) applied to agent operations. Just as the security triad defines what you protect and how, the governance triad defines what the agent can do and how it is accountable.

### DO: The Autonomous Action Scope

DO actions are fully automated. The agent runs the action without waiting for approval.

**Characteristics of good DO actions:**
- Low blast radius: failure is reversible or limited in scope
- High confidence in correctness: the agent has demonstrated accuracy
- Time-sensitive: waiting for approval would eliminate the value (e.g., immediate incident response)
- Read-only or clearly safe writes (e.g., adding a comment to a ticket)

**Examples at different maturity levels:**
- L1: No autonomous actions — only report
- L2: Add diagnostic comments to PagerDuty incidents
- L3: Restart a pod that has been crashing for >10 minutes
- L4: Scale RDS connection pool parameter within a defined safe range

### APPROVE: The Human-in-the-Loop Gate

APPROVE actions require an approver before execution. The agent proposes the action, describes it precisely, and waits.

**Approval workflow components:**
1. **Proposal:** Agent generates a structured action proposal (what, why, expected outcome, risk)
2. **Notification:** Approver is notified via Slack, PagerDuty, or email
3. **Review window:** Approver has X minutes to approve, reject, or request more information
4. **Escalation:** If no response within the window, escalate to the next approver or abort
5. **Execution:** Upon approval, agent executes the action and logs the approval
6. **Outcome:** Agent reports the result back to the approver

**DevOps analogy:** Change management. A production change requires a CAB (Change Advisory Board) review, an approval signature, and a scheduled window. The agent's approval workflow is the same discipline applied to AI-generated change proposals.

**The approval gate is NOT bureaucratic overhead.** It is the mechanism by which:
- Humans verify the agent's proposal is correct before it acts
- The agent's judgment can be compared to human judgment over time (if they always agree → faster path to L4)
- Accountability is established: who approved what, when

### LOG: The Immutable Audit Trail

LOG means every agent action is recorded — what it ran, what it decided, what it was approved, what happened. The audit log is not optional at enterprise scale.

**What the audit log captures:**
- Action type (diagnostic read, parameter change, ticket update)
- Tool invoked (which CLI command, which API endpoint)
- Inputs used (which instance ID, which time window, which task context)
- Output generated (what the agent concluded or proposed)
- Approval status (auto-approved / awaiting approval / approved by [name] at [time] / rejected)
- Outcome (success, failure, error)

**Why this matters:**
- Post-incident review: "What did the agent do during the incident? When? Was it correct?"
- Compliance: "Was any production change made without authorization?"
- Trust building: "Over the last 30 days, how many of the agent's proposals were approved without modification?"

## 2. Autonomy Maturity Levels

The autonomy spectrum defines how much trust an agent has earned — and therefore how much it can do without human involvement.

### L1: Assistive

**Definition:** The agent observes, diagnoses, and reports. It takes no autonomous actions.

**What it can DO:** Read metrics, read logs, read configuration. Generate reports. Add comments to tickets (if configured as a safe action).

**What requires APPROVE:** Any action that modifies state — configuration changes, restarts, scaling, ticket prioritization.

**Trust profile:** This is the starting level for any new agent. You have not yet validated its accuracy in your specific environment.

**DevOps analogy:** A junior engineer on their first week — you want their analysis and observations, but you review every command before they run it.

### L2: Advisory

**Definition:** The agent takes limited, clearly safe, low-blast-radius actions autonomously. It proposes higher-impact actions for approval.

**What it can DO autonomously:** Add comments and diagnostic findings to incident tickets, update monitoring annotations, post Slack notifications, write to internal documentation.

**What requires APPROVE:** Any state change to infrastructure (restart, scale, parameter modify).

**Trust profile:** The agent has been running at L1 for a period, its diagnoses have been validated as accurate, and it has earned the trust to take limited autonomous actions.

**Promotion criteria from L1:** 30 days of operation, accuracy rate above 90% (diagnoses verified correct by humans), zero false escalations.

### L3: Proposal

**Definition:** The agent can execute specific, well-tested, reversible actions autonomously. It proposes higher-impact actions for approval with detailed justification.

**What it can DO autonomously:** Restart pods that have been crashing for >10 minutes, rollback a failed deployment to the previous version, scale a service within defined bounds, create or update alerts.

**What requires APPROVE:** Infrastructure changes (RDS parameter changes, EC2 instance type changes, security group modifications, cost actions above defined thresholds).

**Trust profile:** The agent has been running at L2, its proposals have been approved without modification in the majority of cases, and it has demonstrated that its judgment on L3-category actions is reliable.

### L4: Semi-Autonomous

**Definition:** The agent takes a wide range of infrastructure actions autonomously, with human approval required only for high-blast-radius or irreversible operations.

**What it can DO autonomously:** All of the above plus parameter tuning within safe ranges, capacity scaling within policy limits, automated remediation of known issue patterns.

**What requires APPROVE:** Irreversible operations (delete, terminate, drop), cost actions above a defined dollar threshold, changes to security boundaries (security groups, IAM), changes outside the agent's defined domain.

**Trust profile:** The agent has been operating in production for an extended period, has a demonstrated track record of correct autonomous action, and has formal governance sign-off for the specific actions it performs autonomously.

**DevOps analogy:** Auto-scaling with auto-remediation — the system takes action automatically within defined safe parameters, with human escalation for out-of-bounds situations.

## 3. Human-in-the-Loop: Approval Gate Design

The approval gate is the most critical component of governance design. Poorly designed approval gates create friction without safety; well-designed ones provide safety without becoming bureaucratic blockers.

### Approval Gate Properties

**Who approves?** Define the approver chain explicitly:
1. Primary approver (e.g., the service owner)
2. Secondary escalation (e.g., the on-call engineer)
3. Final escalation (e.g., the engineering manager or platform team lead)

**What information does the approver receive?** The proposal must contain:
- What action the agent proposes
- Why (evidence leading to the proposal)
- Expected outcome (what should happen if approved)
- Risk (what could go wrong, how to reverse if needed)
- Time window (when is this action most effective)

**How long does the approver have?** Define a timeout and an escalation path for non-response:
- Primary: 5 minutes
- Secondary: 10 minutes (if primary does not respond)
- Timeout action: abort the action, log as "expired" (do not execute without approval)

**DevOps analogy:** A change request with SLA. The CAB has 24 hours to approve a change. If no response, the change is deferred to the next window. The agent's approval gate has the same structure — a time window, escalation, and a default-to-abort when the window expires.

### Approval Fatigue

If you require approval for too many actions, approvers stop reading the proposals carefully. They approve everything to reduce the notification burden — defeating the purpose of approval gates.

**Prevention:**
- L1/L2 actions should not require approval (if they do, they are too impactful for their level)
- Group related minor actions into a single approval (one approval for "5 diagnostic annotations" rather than 5 individual approvals)
- Use notification-based approval for trusted actions: "Agent is taking action X in 5 minutes. Reply STOP to abort." (Rather than "approve before proceeding")

## 4. Trust Building: The Promotion Path

Agents earn higher autonomy levels through demonstrated reliability. The promotion criteria are measurable and auditable — not subjective judgments.

### Standard Promotion Criteria

| From → To | Minimum Criteria |
|-----------|-----------------|
| L1 → L2 | 30 days operation; accuracy rate ≥90%; zero false P1 escalations |
| L2 → L3 | 60 days at L2; proposals approved without modification ≥80% of cases; zero incidents caused by agent actions |
| L3 → L4 | 90 days at L3; autonomous L3 actions successful ≥95%; formal governance review and sign-off |

**"Accuracy rate"** is measured by comparing agent diagnoses to human-verified outcomes. If the agent diagnoses "connection pool exhaustion" and the human on-call confirms that is correct → accuracy +1. If the agent diagnoses "application bug" but the real cause was a network issue → accuracy -1.

**"Proposals approved without modification"** measures whether approvers trust the agent's proposals. High modification rate = agent is proposing incorrectly scoped or insufficiently justified actions. Low modification rate = agent's proposals are accurate and appropriately scoped.

### Demotion Criteria

Agents can lose maturity levels. Automatic demotion triggers:
- Any incident caused by agent autonomous action → demote one level
- Accuracy rate falls below threshold over rolling 30-day window → demote to L2
- False P1 escalation (agent declares P1 incident that humans assess as non-incident) → demotion review

Demotion is not punishment — it is a safety mechanism. An agent that was reliable at L3 but becomes unreliable should return to L2 until the issue is understood and resolved.

## 5. Enterprise Requirements: RBAC, Credential Protection, Rollback

Governance at enterprise scale requires more than agent-level configuration.

### RBAC for Agents

Treat agents as service accounts with defined permissions. Best practice:
- Each agent has its own IAM role with the minimum permissions required for its DO actions
- IAM role used by L1/L2 agents should be read-only
- IAM role used by L3/L4 agents should have write permissions scoped to their specific domain

**DevOps analogy:** Kubernetes service accounts. Each service runs as a service account with only the RBAC permissions it needs. Agents are the same — not "the platform team's admin account" but "the db-health-agent service account with RDS read permissions."

### Credential Protection

Credentials should never appear in:
- Agent context windows (SOUL.md, task prompts)
- Audit logs (logged as "[CREDENTIAL]" not the actual value)
- Agent-generated output (Slack messages, PagerDuty notes)

All credentials are injected via environment variable reference at execution time.

### Rollback Plans for Agent Actions

For every L3/L4 action that modifies infrastructure, a rollback procedure must be defined:
- What command reverses the action?
- What is the recovery time objective if the action has unintended consequences?
- Who is responsible for executing the rollback?

This is analogous to requiring a rollback plan in every change request. The agent cannot approve its own rollback plan — it must be documented by a human before the action is added to the L3/L4 DO list.

## Summary

| Governance Concept | What It Is | DevOps Analogy |
|-------------------|-----------|----------------|
| DO | Actions the agent takes autonomously | Auto-scaling with defined policy |
| APPROVE | Actions requiring human sign-off before execution | Change Advisory Board (CAB) review |
| LOG | Immutable record of all agent actions and approvals | Change log / audit trail |
| L1 Assistive | Observe and report only | Junior engineer, day 1 |
| L2 Advisory | Limited safe autonomous actions | Junior engineer after 30 days |
| L3 Proposal | Specific reversible autonomous actions | Senior engineer with documented approval |
| L4 Semi-autonomous | Wide autonomous scope, approve only high-blast-radius | Site reliability automation with manual override |
| Approval gate | Structured proposal → review → execute or abort | Change request with SLA |
| Promotion criteria | Measurable trust thresholds | Progressive delivery (canary → blue-green → full rollout) |

**The core principle:** Start at L1. Every agent earns higher autonomy through demonstrated reliability in your specific environment. No shortcutting to L4 because the agent "seems reliable" — the audit trail and the metrics are what justify trust.
