# Exploratory: AI-Assisted IaC Projects

These are **exploratory stretch projects** — not required to complete Module 6. They are for participants who finish the main lab early and want to go deeper, or who want to apply the patterns to a more realistic scope.

Each project extends the work from the main lab tracks. They are designed to be completable independently — no teammate is required.

---

## Project 1: Multi-Environment Terraform

**Estimated time:** 30 minutes
**Extends:** Track A (Terraform)
**Prerequisites:** Track A lab completed, `terraform validate` passing

### What You Will Build

Extend the `ec2-monitored` Terraform module to support three environments: `dev`, `staging`, and `prod`. Each environment has different instance sizes, alarm thresholds, and notification emails — generated by AI using guided context engineering.

### Challenge

The key challenge is showing AI how environment inheritance works in Terraform. A naive approach generates three nearly identical modules. The correct approach uses a single reusable module with environment-specific `tfvars` files that override the defaults.

### Steps

**1. Update your CLAUDE.md to add environment context:**

```markdown
## Environments
- dev: t2.micro, alarm_threshold 90 (tolerant), notify dev-team@example.com
- staging: t2.micro, alarm_threshold 80 (default), notify staging-alerts@example.com
- prod: t2.micro (free tier constraint), alarm_threshold 70 (strict), notify ops@example.com
```

**2. Ask Claude Code to generate environment-specific directories:**

```
Based on the CLAUDE.md environment context and the ec2-monitored module, generate:
1. environments/dev/terraform.tfvars — with dev-specific values
2. environments/staging/terraform.tfvars — with staging-specific values
3. environments/prod/terraform.tfvars — with prod-specific values

Each tfvars file should set: instance_name, alarm_threshold, notification_email
```

**3. Validate all three environments:**

```bash
for env in dev staging prod; do
  echo "=== Validating $env ==="
  terraform validate
  terraform plan -var-file="environments/$env/terraform.tfvars" -input=false 2>&1 | tail -5
done
```

### Expected Deliverable

Three `terraform.tfvars` files in `environments/dev/`, `environments/staging/`, and `environments/prod/` that all pass `terraform validate`. The alarm thresholds should differ by environment (90/80/70) as specified in CLAUDE.md.

### Teaching Point

The multi-environment pattern demonstrates context engineering at the module level: instead of changing the Terraform module for each environment, you change the context (tfvars) and let the module remain static. The CLAUDE.md is the bridge — it tells AI what the environment conventions are so it generates consistent, convention-following tfvars.

## Project 2: ArgoCD App-of-Apps

**Estimated time:** 30 minutes
**Extends:** Track B (ArgoCD/GitOps)
**Prerequisites:** Track B lab completed, reference app synced successfully

### What You Will Build

Create an ArgoCD Application that manages other Applications — the "app-of-apps" pattern. A parent Application CRD points to a directory in Git that contains child Application CRDs. ArgoCD deploys the parent, which then deploys all the children.

### Challenge

The app-of-apps pattern requires a specific directory structure in your Git repository. ArgoCD must be able to find the child Application CRDs at a predictable path. AI often generates the parent Application CRD correctly but places child applications at paths that do not match the parent's source path.

### Steps

**1. Update your CLAUDE.md to add app-of-apps context:**

```markdown
## App-of-Apps Pattern
- Parent Application: argocd/apps-parent, source path: argocd/apps/
- Child applications: one per file in argocd/apps/ directory
- All child Application CRDs are in namespace: argocd
- All child apps deploy workloads to namespace: app
```

**2. Create the directory structure:**

```bash
mkdir -p argocd/apps
```

**3. Ask Claude Code to generate the parent Application CRD:**

```
Based on the CLAUDE.md app-of-apps context, generate:
1. argocd/apps-parent.yaml — parent Application CRD that points to argocd/apps/ in my GitHub fork
2. argocd/apps/reference-app.yaml — child Application CRD for the reference app (same as the argocd-app.yaml from the lab)
3. argocd/apps/monitoring.yaml — child Application CRD for a hypothetical monitoring namespace (path: monitoring/, namespace: monitoring, automated sync)
```

**4. Validate the structure:**

```bash
kubectl apply --dry-run=client -f argocd/apps-parent.yaml
kubectl apply --dry-run=client -f argocd/apps/reference-app.yaml
```

**5. Push and deploy:**

```bash
git add argocd/
git commit -m "feat: add app-of-apps pattern for GitOps"
git push origin main
kubectl apply -f argocd/apps-parent.yaml
```

### Expected Deliverable

A parent Application CRD (`argocd/apps-parent.yaml`) and at least one child Application CRD (`argocd/apps/reference-app.yaml`). The parent should pass `kubectl apply --dry-run=client`.

### Teaching Point

The app-of-apps pattern is how production GitOps scales from one application to dozens. Instead of manually `kubectl apply`-ing each Application CRD, you manage one parent that manages all the others. Changes to what is deployed go through Git pull requests against the `argocd/apps/` directory. The context engineering lesson: CLAUDE.md must describe the directory structure convention or AI will generate child applications at arbitrary paths.

## Project 3: Cross-Track Integration

**Estimated time:** 45 minutes
**Extends:** Both Track A and Track B
**Prerequisites:** Both Track A and Track B labs completed

### What You Will Build

Combine the two lab tracks: use Terraform to provision the underlying AWS infrastructure, then use ArgoCD to deploy the application workload on top of it. This is the real-world pattern used in production: Terraform manages cloud resources (VPCs, RDS, S3), ArgoCD manages application deployment (Kubernetes workloads).

### Challenge

The coordination challenge: Terraform produces outputs (VPC IDs, security group ARNs, RDS connection strings) that become inputs to the application deployment. In a real system, these values flow from Terraform's state into Kubernetes secrets or Helm values, which ArgoCD then applies to the cluster. AI must understand both layers to generate code that fits together.

### Steps

**1. Update your CLAUDE.md to describe the cross-layer architecture:**

```markdown
## Cross-Layer Architecture
- Terraform layer: Provisions EC2 + CloudWatch + SNS (Track A module)
- Kubernetes layer: Deploys reference app via ArgoCD (Track B)
- Coordination: Terraform outputs become Kubernetes ConfigMap values
- Terraform outputs needed: instance_id, instance_public_ip, sns_topic_arn
```

**2. Ask Claude Code to generate the coordination layer:**

```
Based on the CLAUDE.md cross-layer context, generate:
1. A Terraform local-exec provisioner that writes Terraform outputs to a
   kubernetes-config.json file after apply
2. A bash script (inject-config.sh) that reads kubernetes-config.json and
   creates a Kubernetes ConfigMap in the app namespace
3. Update the ArgoCD Application CRD to add a postSync hook that runs
   inject-config.sh after each sync

The goal is: terraform apply writes infra outputs, inject-config.sh creates
the ConfigMap, ArgoCD sync hook ensures it runs after each deployment.
```

**3. Validate the generated components:**

```bash
# Terraform layer
terraform validate
terraform plan -input=false 2>&1 | tail -10

# Kubernetes layer
kubectl apply --dry-run=client -f argocd-app-with-hook.yaml
```

### Expected Deliverable

Three artifacts: a Terraform `local-exec` block that writes outputs, an `inject-config.sh` script, and an updated ArgoCD Application CRD with a postSync hook. All should pass their respective validation commands.

### Teaching Point

Real infrastructure has layers. Terraform manages the cloud substrate; Kubernetes manages the application layer. The AI-generated coordination script is only as good as the context you provide — CLAUDE.md must describe the output names, the target namespace, and the hook timing. Without that context, AI generates code that assumes a different architecture or skips the coordination step entirely.

This project demonstrates context engineering at architectural scale: you are not generating individual resources, you are encoding the relationships between infrastructure layers.

## Which Project Should You Do?

| Your Background | Recommended Project |
|----------------|--------------------|
| Strong Terraform, new to GitOps | Project 1 to deepen Track A, then Project 3 |
| Strong Kubernetes, new to Terraform | Project 2 to deepen Track B, then Project 3 |

| Less than 30 minutes available | Project 1 — most self-contained stretch |

All three projects are **exploratory** — they extend the lab patterns without introducing fundamentally new tools. The goal is to experience context engineering at a larger scope than the base lab provides.
