# Lab: Structured AI Coding — Track A (Helm Chart)

**Duration:** 60 minutes
**Deliverable:** Production-quality Helm chart with HPA, PDB, ServiceMonitor, resource limits, and NOTES.txt

## What You Need

- **Claude Code** (primary) — open in your terminal with `claude`
- **Crush** (alternative) — open with `crush` if using a different LLM provider
- KIND cluster running with reference app deployed (verify: `kubectl get pods -n app`)
- Existing Helm chart at `reference-app/helm/reference-app/` in the repo root
- Helm 3.x installed (`helm version` should show v3.x)

---

## Step 0: Baseline Analysis

Before touching AI, you need to know what you're starting from. Open the existing Helm chart and inventory it manually.

```bash
ls reference-app/helm/reference-app/templates/
```

**What the existing chart has:**

- Deployments for all 4 services (api-gateway, catalog, worker, dashboard)
- `livenessProbe` and `readinessProbe` for each service (HTTP GET to `/health/live` and `/health/ready`)
- Resource requests (`cpu: 50m`, `memory: 64Mi` per service)
- ConfigMap for environment variables
- NodePort for the dashboard service

Write down what you observe. Now ask yourself: **is this production-ready?**

**Expected result:** You identify these 6 gaps missing from the baseline chart:

1. Resource limits (requests exist, but no limits — pods can burst unconstrained)
2. HorizontalPodAutoscaler (no auto-scaling based on load)
3. PodDisruptionBudget (no minimum availability guarantee during node maintenance)
4. ServiceMonitor (Prometheus cannot scrape these services — no monitoring)
5. NOTES.txt (no post-install guidance for operators)
6. `helm lint` warnings (chart may have cleanable issues)

This gap list is your specification. You'll feed it to AI in structured phases.

---

## Phase 1: Brainstorm

Open Claude Code or Crush. Start a **fresh conversation**. Paste this context exactly:

```
I have a Helm chart for a microservices reference app (api-gateway on 8080,
catalog on 8081, worker on 8082, dashboard). The chart already has Deployments
with liveness/readiness probes and resource requests. I need to make it
production-quality. What's missing?
```

Read the AI response carefully.

**Expected result:** AI identifies at least these gaps — HPA, PDB, resource limits, ServiceMonitor, NOTES.txt. The list should substantially overlap with your manual gap analysis from Step 0.

**Reflection:** Did AI find anything you missed? Did it suggest things that aren't appropriate for this chart (e.g., Ingress when you're using NodePort)? Note the differences — that gap between AI output and your domain knowledge is why structured context matters.

---

## Phase 2: Design

Start a **new conversation**. You are going to give AI the full 4-layer context model before asking for a design. This is the most important step — it sets the frame for all generation that follows.

Paste this context block:

```
I am an SRE building production Kubernetes infrastructure.

Task: Add HPA, PDB, ServiceMonitor, resource limits, and NOTES.txt to the
reference app Helm chart

System:
- KIND cluster running Kubernetes 1.32
- Helm 3.18
- kube-prometheus-stack deployed in the monitoring namespace
- Services: api-gateway (port 8080), catalog (port 8081), worker (port 8082)
- All services expose /health/ready for readiness and Prometheus metrics

Constraints:
- Use Helm 3 template syntax only
- Kubernetes 1.32 stable APIs only — no alpha or beta APIs
- ServiceMonitor requires matchLabels: release: prometheus to be discovered
  by the kube-prometheus-stack operator

Produce a design document listing each new template file I need to create,
its Kubernetes API version and kind, and a one-line description of its purpose.
```

**Expected result:** A structured plan listing 5 new template files:

1. `hpa.yaml` — `autoscaling/v2`, `HorizontalPodAutoscaler`, scales deployments on CPU
2. `pdb.yaml` — `policy/v1`, `PodDisruptionBudget`, ensures minimum availability
3. `servicemonitor.yaml` — `monitoring.coreos.com/v1`, `ServiceMonitor`, Prometheus scraping
4. Resource limits patch (additions to existing deployment templates)
5. `NOTES.txt` — post-install instructions template

If AI starts generating YAML at this stage, redirect it: "Don't write code yet — just the design document."

---

## Phase 3: Blueprint

Continue the **same conversation** from Phase 2 (keep the context). Ask:

```
Now generate skeleton YAML files for each template in the design. Include only:
- apiVersion
- kind
- metadata (name, namespace, labels using Helm template variables)
- An empty spec: {}

No implementation details yet. Just the structure.
```

**Expected result:** 5 skeleton YAML files using Helm template syntax. Each file should look roughly like:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: {{ include "reference-app.fullname" . }}-api-gateway
  labels:
    {{- include "reference-app.labels" . | nindent 4 }}
spec: {}
```

If a skeleton uses hardcoded names instead of `{{ include "reference-app.fullname" . }}`, that's a context engineering gap — the AI didn't know about your `_helpers.tpl` naming conventions. Note it for the implement phase.

---

## Phase 4: Implement

Continue the **same conversation**. Now provide the exact production values and ask AI to fill them in:

```
Fill in the complete spec for each template using these exact values:

HPA (all three services — api-gateway, catalog, worker):
- minReplicas: 2
- maxReplicas: 5
- target CPU utilization: 70%
- scaleDown stabilizationWindowSeconds: 300

PDB (all three services):
- minAvailable: 1

ServiceMonitor (all three services):
- scrape path: /health/ready
- scrapeInterval: 30s
- selector matchLabels: app.kubernetes.io/name=reference-app
- namespaceSelector: monitoring namespace
- release: prometheus label required for kube-prometheus-stack discovery

Resource limits (add to existing deployments — api-gateway, catalog, worker):
- cpu: 500m
- memory: 256Mi

NOTES.txt:
- Post-install message showing how to get the dashboard URL
- How to check HPA status: kubectl get hpa -n {{ .Release.Namespace }}
- How to verify ServiceMonitor was picked up by Prometheus
```

**Expected result:** Complete, populated YAML for all 5 additions. The files should be immediately usable — not placeholders, not TODOs.

<details>
<summary>Solution: hpa.yaml — click to compare your output</summary>

```yaml
{{- range $service := list "api-gateway" "catalog" "worker" }}
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: {{ include "reference-app.fullname" $ }}-{{ $service }}
  labels:
    {{- include "reference-app.labels" $ | nindent 4 }}
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: {{ include "reference-app.fullname" $ }}-{{ $service }}
  minReplicas: 2
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
{{- end }}
```

</details>

<summary>Solution: servicemonitor.yaml — click to compare your output</summary>

```yaml
{{- range $service, $port := dict "api-gateway" 8080 "catalog" 8081 "worker" 8082 }}
---
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: {{ include "reference-app.fullname" $ }}-{{ $service }}

  selector:
    matchLabels:
      app.kubernetes.io/name: reference-app
      app.kubernetes.io/component: {{ $service }}
  namespaceSelector:
    matchNames:
      - app
  endpoints:
    - port: http
      path: /health/ready
      interval: 30s
{{- end }}
```

</details>

<summary>Solution: Resource limits patch for values.yaml — click to compare your output</summary>

Add `limits` blocks under each service's `resources:` in `values.yaml`:

```yaml
apiGateway:
  resources:
    requests:
      cpu: 50m
      memory: 64Mi
    limits:
      cpu: 500m
      memory: 256Mi

catalog:
  resources:
    requests:
      cpu: 50m
      memory: 64Mi
    limits:
      cpu: 500m
      memory: 256Mi

worker:
  resources:
    requests:
      cpu: 50m
      memory: 64Mi
    limits:
      cpu: 500m
      memory: 256Mi
```

And in each deployment template, add `limits` to the resources block:

```yaml
resources:
  requests:
    cpu: {{ .Values.apiGateway.resources.requests.cpu }}
    memory: {{ .Values.apiGateway.resources.requests.memory }}
  limits:
    cpu: {{ .Values.apiGateway.resources.limits.cpu }}
    memory: {{ .Values.apiGateway.resources.limits.memory }}
```

</details>

## Phase 5: Validate

Apply the generated templates and verify everything works.

**Step 5a: Run helm lint**

```bash
helm lint reference-app/helm/reference-app/
```

**Expected result:** `0 chart(s) with warnings` and `0 chart(s) with errors` — a clean lint pass. If there are errors, read them carefully. Most lint errors are YAML indentation issues or missing required fields — fix them and re-run.

**Step 5b: Dry-run render**

```bash
helm template reference-app reference-app/helm/reference-app/ | grep "^kind:" | sort | uniq -c
```

**Expected result:** Output includes all new resource kinds:

```
      3 kind: HorizontalPodAutoscaler
      3 kind: PodDisruptionBudget
      3 kind: ServiceMonitor
```

If a kind is missing, check that the template file was created in the correct directory and that any conditional `{{ if }}` blocks are satisfied.

**Step 5c: Full template render**

```bash
helm template reference-app reference-app/helm/reference-app/ > /tmp/reference-app-rendered.yaml
wc -l /tmp/reference-app-rendered.yaml
```

**Expected result:** A rendered YAML file substantially larger than the baseline — you've added roughly 150-200 lines of production configuration. Review the file to confirm the HPA, PDB, and ServiceMonitor specs match the solution blocks above.

**Step 5d: Compare against solution**

Open the solution blocks in Phase 4 and compare key fields:

- HPA: `averageUtilization: 70`, `stabilizationWindowSeconds: 300`
- PDB: `minAvailable: 1`
- ServiceMonitor: `release: prometheus` label present, `interval: 30s`

**Expected result:** Your generated output matches the solution structure and values. Minor formatting differences (indentation, comment style) are fine — the semantic content should match.

## Reflection

Trace each design decision back to the workflow phase that produced it:

| Decision | Where It Came From |
|----------|--------------------|
| HPA minReplicas: 2 | Phase 4 — explicit constraint in implementation context |
| `release: prometheus` label on ServiceMonitor | Phase 2 — system context specified kube-prometheus-stack discovery requirement |
| `stabilizationWindowSeconds: 300` | Phase 4 — prevents flapping during traffic spikes |
| Helm template variables (`{{ include }}`) | Phase 3 — blueprint used `_helpers.tpl` naming conventions |
| Stable `autoscaling/v2` API | Phase 2 — constraint specified Kubernetes 1.32 stable APIs only |

**The structured workflow gave you:**

1. **Phase 1 (Brainstorm):** A complete gap list — nothing production-critical was missed because AI inventoried the baseline systematically
2. **Phase 2 (Design):** A structured architecture — AI planned before it coded, which prevents the "generate and pray" anti-pattern
3. **Phase 3 (Blueprint):** Structural consistency — all templates follow the same naming conventions from the start
4. **Phase 4 (Implement):** Precise values — because you provided exact constraints, AI didn't guess at thresholds
5. **Phase 5 (Validate):** Confidence — `helm lint` passed, the template renders, output matches solution

Compare this to a single-shot approach: "Generate a production Helm chart for my microservices app." That prompt produces something generic. This workflow produces something that works for your specific system, with your specific constraints, using your specific tool versions.

That's context engineering applied to infrastructure code.
