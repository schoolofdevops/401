# Lab: Structured AI Coding — Track B (CI/CD Pipeline)

**Duration:** 60 minutes
**Deliverable:** Production-quality GitHub Actions CI/CD pipeline with matrix testing, OIDC auth, environment-specific deploy jobs, and proper image tagging

## What You Need

- **Claude Code** (primary) — open in your terminal with `claude`
- **Crush** (alternative) — open with `crush` if using a different LLM provider
- GitHub account (Actions runs on push/PR — free for public repos and included in GitHub plans)
- Existing CI/CD pipeline at `.github/workflows/ci.yml` in the repo root
- Familiarity with the reference app (4 services: api-gateway, catalog, worker, dashboard)

---

## Step 0: Baseline Analysis

Before touching AI, read the existing pipeline and inventory what it does. Open `.github/workflows/ci.yml`.

```bash
cat .github/workflows/ci.yml
```

**What the existing pipeline has:**

- `cargo test --workspace` — runs unit tests for all Rust services
- Docker image builds for all 4 services
- KIND cluster creation via `helm/kind-action`
- Helm deploy of the reference app to the KIND cluster
- Health endpoint verification via `curl` and `kubectl port-forward`

This pipeline works for development validation. Ask yourself: **would you put this in front of a production deployment?**

**Expected result:** You identify these 5 gaps missing from the baseline pipeline:

1. No matrix strategy — tests run against a single Rust version (latest stable). MSRV (minimum supported Rust version) is untested.
2. No OIDC-based AWS credential exchange — if production needs ECR or S3, you'd need to store long-lived AWS secrets, which is a security anti-pattern
3. No separate staging/production deploy jobs — the single job deploys to whatever environment with no gate
4. No `docker/metadata-action` — image tags are hardcoded to `ci`, losing traceability (no SHA, no semver, no branch tags)
5. No job summary — after the pipeline runs, there's no structured output showing what was deployed where

This gap list is your specification. You'll feed it to AI in structured phases.

## Phase 2: Design

Start a **new conversation**. You are going to give AI the full 4-layer context model before asking for a design. This is the most important step — it sets the frame for all generation that follows.

Paste this context block:

```
I am a DevOps engineer building production CI/CD for a Rust microservices app.

Task: Add matrix testing, OIDC auth, staging/production deploy jobs,
docker/metadata-action image tagging, and a job summary to the existing
GitHub Actions pipeline

System:
- GitHub Actions (ubuntu-latest runners)
- Docker for image builds
- KIND cluster for integration testing
- Helm 3.18 for deploys
- 3 Rust services: api-gateway, catalog, worker (plus a Node.js dashboard)
- Existing ci.yml already has: test job, build-and-deploy job

Constraints:
- GitHub Actions workflow syntax (YAML, .github/workflows/)
- OIDC requires aws-actions/configure-aws-credentials@v4 with permissions:
  id-token: write, contents: read
- Use reusable workflow steps (composite actions) where it reduces repetition
- Production deploy job must require manual approval via GitHub environments
- Matrix should test Rust 1.75 (MSRV) and 1.78 (stable)

Produce a pipeline design document with: job names, trigger conditions,
job dependency graph (needs:), and which jobs correspond to which environment.
Do not write YAML yet — just the design.
```

**Expected result:** A structured plan showing:

- Trigger: `push` to main, `pull_request`
- `build-test` job with matrix `[1.75, 1.78]`
- `build-images` job (needs: build-test) — builds and tags Docker images
- `staging-deploy` job (needs: build-images) — deploys to KIND, runs smoke tests
- `production-deploy` job (needs: staging-deploy) — requires manual approval via `environment: production`
- Job dependency graph: `build-test` → `build-images` → `staging-deploy` → `production-deploy`

If AI starts writing YAML at this stage, redirect it: "Don't write workflow YAML yet — just the design document with job names and dependencies."

## Phase 3: Blueprint

Continue the **same conversation** from Phase 2 (keep the context). Ask:

```
Now generate a skeleton workflow file with:
- The correct triggers (push to main, pull_request)
- All job names and their needs: dependencies
- The matrix strategy block for build-test (just the matrix, not the steps)
- Correct permissions block for OIDC
- Empty steps: [] for each job

No step implementations yet. Just the structure.
```

**Expected result:** A skeleton `.github/workflows/ci.yml` that looks roughly like:

```yaml
name: Reference App CI

on:
  push:
    branches: [main]
    paths:
      - 'reference-app/**'
      - '.github/workflows/ci.yml'
  pull_request:
    paths:
      - 'reference-app/**'

permissions:
  id-token: write
  contents: read

jobs:
  build-test:
    name: Build and Test (Rust ${{ matrix.rust }})
    runs-on: ubuntu-latest
    strategy:
      matrix:
        rust: ['1.75', '1.78']
    steps: []

  build-images:
    name: Build Docker Images
    needs: build-test
    runs-on: ubuntu-latest
    steps: []

  staging-deploy:
    name: Deploy to Staging (KIND)
    needs: build-images
    runs-on: ubuntu-latest
    steps: []

  production-deploy:
    name: Deploy to Production
    needs: staging-deploy
    environment: production
    runs-on: ubuntu-latest
    steps: []
```

If the skeleton is missing the `needs:` chain, `matrix:`, or `permissions:` block, ask AI to add them before proceeding. The skeleton is the contract — get it right before implementing.

## Phase 4: Implement

Continue the **same conversation**. Now provide the exact implementation details for each job:

```
Fill in all steps for each job using these exact specifications:

build-test job (matrix: rust 1.75 and 1.78):
- actions/checkout@v4
- dtolnay/rust-toolchain with toolchain: ${{ matrix.rust }}
- Swatinem/rust-cache@v2 with workspaces: "reference-app"
- cargo test --workspace in reference-app/ directory

build-images job:
- actions/checkout@v4
- docker/setup-buildx-action@v3
- docker/metadata-action@v5 for each service:
  images: ghcr.io/${{ github.repository }}/api-gateway
  tags:
    type=sha,prefix=sha-,format=short
    type=ref,event=branch
    type=semver,pattern={{version}}
- docker build for api-gateway, catalog, worker services
  build-arg GIT_SHA=${{ github.sha }}
  tag with the metadata-action output tags

staging-deploy job:
- actions/checkout@v4
- helm/kind-action@v1 with config: infrastructure/kind/cluster-config.yaml
- azure/setup-helm@v4
- Deploy PostgreSQL via bitnami chart (same as existing ci.yml)
- Deploy reference-app via Helm using the sha-short image tag from build-images
- Verify health endpoints via kubectl port-forward + curl

production-deploy job (environment: production, needs manual approval):
- actions/checkout@v4
- aws-actions/configure-aws-credentials@v4 with role-to-assume from secrets
  (OIDC — no long-lived credentials stored)
- Login to Amazon ECR
- Push images to ECR using the semver tag from build-images
- Write job summary using $GITHUB_STEP_SUMMARY showing:
  - Deployed image tags
  - Staging health check result (pass/fail)
  - Production ECR push confirmation
```

**Expected result:** A complete workflow YAML with all jobs and steps filled in. The production-deploy job should require the `environment: production` approval gate. The matrix should run `build-test` twice (once for each Rust version). Image tags should include `sha-` prefixed short SHAs from `docker/metadata-action`.

<details>
<summary>Solution: Complete production pipeline — click to compare your output</summary>

```yaml
name: Reference App CI

on:
  push:
    branches: [main]
    paths:
      - 'reference-app/**'
      - '.github/workflows/ci.yml'
  pull_request:
    paths:
      - 'reference-app/**'

permissions:
  id-token: write
  contents: read
  packages: write

env:
  CLUSTER_NAME: lab

jobs:
  build-test:
    name: Test (Rust ${{ matrix.rust }})
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        rust: ['1.75', '1.78']
    steps:
      - uses: actions/checkout@v4

      - name: Install Rust ${{ matrix.rust }}
        uses: dtolnay/rust-toolchain@master
        with:
          toolchain: ${{ matrix.rust }}

      - name: Cache Rust dependencies
        uses: Swatinem/rust-cache@v2
        with:
          workspaces: "reference-app"
          key: ${{ matrix.rust }}

      - name: Run unit tests
        working-directory: reference-app
        run: cargo test --workspace

  build-images:
    name: Build and Tag Docker Images
    needs: build-test
    runs-on: ubuntu-latest
    outputs:
      sha-tag: ${{ steps.meta-gateway.outputs.version }}
    steps:
      - uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Login to GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Extract metadata (api-gateway)
        id: meta-gateway
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}/api-gateway
          tags: |
            type=sha,prefix=sha-,format=short
            type=ref,event=branch
            type=semver,pattern={{version}}

      - name: Extract metadata (catalog)
        id: meta-catalog
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}/catalog
          tags: |
            type=sha,prefix=sha-,format=short
            type=ref,event=branch
            type=semver,pattern={{version}}

      - name: Extract metadata (worker)
        id: meta-worker
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}/worker
          tags: |
            type=sha,prefix=sha-,format=short
            type=ref,event=branch
            type=semver,pattern={{version}}

      - name: Build and push api-gateway
        uses: docker/build-push-action@v6
        with:
          context: reference-app/services/api-gateway
          push: true
          tags: ${{ steps.meta-gateway.outputs.tags }}
          build-args: GIT_SHA=${{ github.sha }}

      - name: Build and push catalog
        uses: docker/build-push-action@v6
        with:
          context: reference-app/services/catalog
          push: true
          tags: ${{ steps.meta-catalog.outputs.tags }}
          build-args: GIT_SHA=${{ github.sha }}

      - name: Build and push worker
        uses: docker/build-push-action@v6
        with:
          context: reference-app/services/worker
          push: true
          tags: ${{ steps.meta-worker.outputs.tags }}
          build-args: GIT_SHA=${{ github.sha }}

  staging-deploy:
    name: Deploy to Staging (KIND)
    needs: build-images
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Create KIND cluster
        uses: helm/kind-action@v1
        with:
          config: infrastructure/kind/cluster-config.yaml
          cluster_name: ${{ env.CLUSTER_NAME }}

      - name: Install Helm
        uses: azure/setup-helm@v4

      - name: Deploy PostgreSQL
        run: |
          helm repo add bitnami https://charts.bitnami.com/bitnami
          helm repo update
          helm upgrade --install postgresql bitnami/postgresql \
            --namespace db --create-namespace \
            --set auth.username=refapp \
            --set auth.password=refapp-lab-password \
            --set auth.database=refapp \
            --wait --timeout 120s

      - name: Deploy reference app (staging)
        run: |
          SHA_TAG="sha-$(echo ${{ github.sha }} | cut -c1-7)"
          helm upgrade --install reference-app reference-app/helm/reference-app \
            --namespace app --create-namespace \
            --set apiGateway.image.repository=ghcr.io/${{ github.repository }}/api-gateway \
            --set apiGateway.image.tag=$SHA_TAG \
            --set catalog.image.repository=ghcr.io/${{ github.repository }}/catalog \
            --set catalog.image.tag=$SHA_TAG \
            --set worker.image.repository=ghcr.io/${{ github.repository }}/worker \
            --set worker.image.tag=$SHA_TAG \
            --wait --timeout 120s

      - name: Smoke test staging
        run: |
          kubectl port-forward -n app svc/reference-app-api-gateway 8080:8080 &
          PF_PID=$!
          sleep 5
          curl -sf http://localhost:8080/health/ready | jq .
          kill $PF_PID || true

  production-deploy:
    name: Deploy to Production (ECR)
    needs: staging-deploy
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_DEPLOY_ROLE_ARN }}
          aws-region: us-east-1

      - name: Login to Amazon ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Push images to ECR
        run: |
          ECR_REGISTRY=${{ steps.login-ecr.outputs.registry }}
          SHA_TAG="sha-$(echo ${{ github.sha }} | cut -c1-7)"
          for SERVICE in api-gateway catalog worker; do
            docker pull ghcr.io/${{ github.repository }}/$SERVICE:$SHA_TAG
            docker tag  ghcr.io/${{ github.repository }}/$SERVICE:$SHA_TAG \
                        $ECR_REGISTRY/reference-app/$SERVICE:$SHA_TAG
            docker push $ECR_REGISTRY/reference-app/$SERVICE:$SHA_TAG
          done

      - name: Write deployment summary
        run: |
          SHA_TAG="sha-$(echo ${{ github.sha }} | cut -c1-7)"
          ECR_REGISTRY=${{ steps.login-ecr.outputs.registry }}
          cat >> $GITHUB_STEP_SUMMARY <<EOF
          ## Deployment Summary

          | Service | Image Tag | Registry |
          |---------|-----------|----------|
          | api-gateway | $SHA_TAG | $ECR_REGISTRY |
          | catalog     | $SHA_TAG | $ECR_REGISTRY |
          | worker      | $SHA_TAG | $ECR_REGISTRY |

          **Staging:** Smoke tests passed
          **Production:** Images pushed to ECR — manual deploy to production cluster required
          EOF
```

## Phase 5: Validate

Verify the generated pipeline is correct before pushing it to GitHub.

**Step 5a: YAML syntax check**

```bash
# If you have yamllint installed:
yamllint .github/workflows/ci.yml

# If you have actionlint installed (recommended for GitHub Actions):
actionlint .github/workflows/ci.yml

# Minimal check with Python (available everywhere):
python3 -c "import yaml, sys; yaml.safe_load(open('.github/workflows/ci.yml'))" && echo "Valid YAML"
```

**Expected result:** No syntax errors. If `actionlint` reports type errors in `needs:` or `outputs:` references, fix them before proceeding — these cause silent failures in real pipelines.

**Step 5b: Mental walkthrough — trace the job graph**

Walk through the pipeline manually:

1. Push to main branch triggers the workflow
2. `build-test` runs in parallel for Rust 1.75 and 1.78 — both must pass
3. `build-images` starts only after both matrix jobs complete (needs: build-test)
4. `staging-deploy` starts after `build-images` — deploys to KIND, runs smoke tests
5. `production-deploy` starts after `staging-deploy` — but pauses for manual approval via the `environment: production` gate

**Expected result:** You can trace a push event through all 4 jobs without gaps or circular dependencies. The matrix runs `build-test` twice. `production-deploy` requires human approval.

**Step 5c: Verify OIDC permissions**

Check that the workflow has the correct top-level `permissions:` block:

```yaml
permissions:
  id-token: write    # required for OIDC token exchange
  contents: read     # required for checkout
  packages: write    # required for ghcr.io push
```

**Expected result:** All three permissions present. Without `id-token: write`, OIDC authentication will fail silently.

**Step 5d: Compare against solution**

Open the solution block in Phase 4 and compare key structural elements:

- `strategy.matrix.rust: ['1.75', '1.78']` in `build-test`
- `docker/metadata-action@v5` in `build-images`
- `environment: production` in `production-deploy`
- `$GITHUB_STEP_SUMMARY` job summary in `production-deploy`

**Expected result:** Your generated pipeline matches the solution structure. Minor differences in step ordering or action versions are acceptable — the job dependency graph and security posture (OIDC, not static secrets) must match.

## Reflection

Trace each design decision back to the workflow phase that produced it:

| Decision | Where It Came From |
|----------|--------------------|
| Rust 1.75 as MSRV in matrix | Phase 2 — system context specified MSRV testing requirement |
| `docker/metadata-action` for image tags | Phase 1 — Brainstorm identified hardcoded `ci` tags as a production gap |
| `environment: production` approval gate | Phase 2 — design specified production job requires manual approval |
| OIDC via `aws-actions/configure-aws-credentials@v4` | Phase 2 — constraint specified no long-lived secrets |
| `$GITHUB_STEP_SUMMARY` for deployment visibility | Phase 4 — implementation context specified job summary output |

**The structured workflow gave you:**

1. **Phase 1 (Brainstorm):** A complete gap list — the 5 production-quality items identified before writing a single line of YAML
2. **Phase 2 (Design):** A job dependency graph — AI planned the workflow structure before implementing any steps, preventing the "one big job" anti-pattern
3. **Phase 3 (Blueprint):** A skeleton with correct `needs:` chains — structure locked in before you could confuse it with implementation details
4. **Phase 4 (Implement):** Precise steps — because you provided exact action versions, registry URLs, and output variable names, AI didn't guess
5. **Phase 5 (Validate):** Confidence — YAML syntax passes, job graph traces correctly, OIDC permissions verified before pushing to GitHub

Compare this to a single-shot approach: "Generate a production GitHub Actions pipeline for my Rust microservices app." That prompt produces something generic — probably missing OIDC, probably missing the matrix, probably deploying to a single environment. This workflow produces a pipeline that reflects your specific security requirements, your specific Rust version support policy, and your specific deployment environments.

That's context engineering applied to CI/CD infrastructure.

## Comparison: Track A vs Track B

Both tracks applied the same 5-phase structured workflow. The tool changed (Helm chart vs GitHub Actions YAML), but the pattern was identical:

| Phase | Track A (Helm) | Track B (CI/CD) |
|-------|----------------|-----------------|
| Brainstorm | HPA, PDB, ServiceMonitor gaps | Matrix, OIDC, env-specific deploy gaps |
| Design | 4-layer context with K8s version constraints | 4-layer context with GitHub Actions constraints |
| Blueprint | Skeleton YAML with Helm template vars | Skeleton workflow with job names and needs: |
| Implement | Exact thresholds, labels, scrape intervals | Exact action versions, registry, permissions |
| Validate | `helm lint` + `helm template` | `yamllint` + mental job graph trace |

This is the core insight: the **workflow is transferable**. Whether you're building Terraform modules, Ansible playbooks, ArgoCD ApplicationSets, or any other infrastructure artifact — the same 5 phases, the same context-first approach, the same structured hand-off from phase to phase.
